基于AWS Serverless的视频点播平台的设计与实现
摘　要
随着在线视频业务的持续发展，传统视频平台在存储、转码与分发等环节面临扩展成本高、运维复杂和资源利用不均衡等问题。针对这些问题，本文设计并实现了一套基于 AWS Serverless 架构的视频点播平台。系统以前端应用、关系型数据库和云端媒体处理链路共同组成了系统的整体架构，采用 Next.js 16 与 React 19 构建前端，使用 PostgreSQL 与 Prisma 完成数据建模和持久化，并借助 Better Auth 实现用户认证与权限控制。在媒体处理方面，平台通过对象存储管理视频文件，利用 Step Functions 编排 Lambda 完成元数据提取、FFmpeg 转码、HLS 切片、封面抽取与状态回写，并结合 EventBridge 实现阶段反馈与状态同步。系统实现了视频上传、处理、发布、播放以及评论、收藏、播放列表和统计分析等功能。结果表明，该平台能够形成较完整的视频点播业务流程，具有较好的模块化、扩展性和可维护性，也说明 AWS Serverless 架构在中小规模视频点播场景中具有较高的应用可行性。

关键词：Serverless；视频点播平台；Next.js；云函数；对象存储；工作流编排


 
Design and Implementation of a Video-on-Demand Platform Based on AWS Serverless Architecture

Abstract
With the continued growth of online video services, traditional video platforms face challenges such as high scaling costs, complex operations, and uneven resource utilization in storage, transcoding, and distribution. To address these issues, this paper designs and implements a video-on-demand platform based on an AWS serverless architecture. The system combines a frontend application, a relational database, and a cloud-based media-processing pipeline. Next.js 16 and React 19 are used to build the frontend, PostgreSQL and Prisma are adopted for data modeling and persistence, and Better Auth is used for authentication and access control. In the media-processing workflow, video files are managed through object storage, while Step Functions orchestrates Lambda functions for metadata extraction, FFmpeg transcoding, HLS packaging, thumbnail generation, and status updates. EventBridge is further introduced to provide stage feedback and state synchronization. The platform supports video upload, processing, publishing, playback, comment interaction, favorites, playlists, and analytics. The results show that the platform forms a relatively complete video-on-demand workflow with good modularity, scalability, and maintainability, demonstrating the practical feasibility of AWS serverless architecture for small and medium-sized video platforms.

Key Words: AWS Serverless; Video-on-Demand Platform; Next.js; Lambda; Object Storage; Workflow Orchestration

第1章	绪论
随着移动互联网、宽带网络和智能终端的普及，在线视频已成为互联网内容消费的重要形态。无论是长视频平台、短视频平台，还是在线教育、企业培训和活动回看系统，视频点播都已经成为数字内容传播的基础能力。与图文类业务相比，视频业务在数据规模、处理链路和分发方式上更为复杂，尤其是在上传、转码、存储、分发和播放等环节，对系统架构的弹性、稳定性和可维护性提出了更高要求。因此，围绕视频点播平台的设计与实现展开研究，具有较强的现实意义和工程价值。
本课题面向中小规模视频业务场景，结合现代 Web 技术与 AWS Serverless 架构，设计并实现一个具备上传、转码、播放、互动、管理和统计能力的视频点播平台。论文在关注系统功能实现的同时，也讨论如何借助对象存储、函数计算、工作流编排和事件驱动机制提升开发效率与资源利用率，从而为同类业务提供一种可复用的实践思路。
1.1 课题背景
近年来，在线视频业务持续增长，用户对视频内容的访问场景也日益多样化，视频平台从单纯的内容展示逐渐转向“内容生产、处理、分发、互动、分析” 全流程覆盖。与此相对应，平台系统不再只需要支持前端页面展示，还必须具备视频上传、异步转码、封面抽取、流媒体播放、评论互动、收藏订阅以及运营统计等完整能力。尤其是在用户自主上传视频的业务场景中，视频源文件大小不一、清晰度和编码格式各异，给平台在媒体处理和资源调度方面带来了显著挑战。
传统视频平台通常采用自建服务器或云主机集群来负责媒体处理任务，通过常驻式转码服务、消息中间件和分发组件完成上传后的处理流程。这类方案在业务规模稳定、资源投入充足的情况下具有一定优势，但其短板也较为明显：一方面，视频处理任务具有波峰波谷明显、资源占用高的特点，固定资源池容易出现高峰期不足、低峰期闲置的问题；另一方面，转码服务、文件存储、任务调度和状态管理等模块往往需要分别部署和维护，系统整体复杂度较高，难以快速响应新业务试错需求。
在云计算快速发展的背景下，以对象存储、函数计算和工作流编排为代表的 Serverless 技术逐渐成熟，为视频平台提供了新的架构思路。相较于传统架构，Serverless 架构能够按需启动计算资源，通过事件驱动方式组织媒体处理流程，将大文件上传、异步转码和状态回写等步骤解耦，降低基础设施维护成本，并提高系统的扩展能力。对于中小型视频平台、教学实验项目或新业务验证场景而言，这种方式具有较高的适用性。
基于上述背景，本文选择以 AWS Serverless 架构为核心，结合 Next.js 16、React 19、PostgreSQL、Prisma、FFmpeg、HLS 和 Better Auth 等技术，设计并实现一套视频点播平台，并围绕其架构合理性与工程可行性展开研究。

2.1 Serverless 架构概述
Serverless指开发者无需直接管理底层服务器资源，应用的计算、扩缩容、运行调度和部分运维能力由云平台负责。该模式通常以函数计算、事件驱动、托管存储和托管工作流为核心，能够在业务请求到来时动态分配资源，在空闲阶段自动回收资源，从而提升资源利用率并降低系统运维复杂度。
对于视频点播平台而言，视频上传、转码、切片、封面抽取和状态回写等任务具有明显的异步处理特征，其访问压力和任务持续时间也呈现出较强的波动性。如果采用传统常驻式服务架构，需要持续维护转码服务、消息队列、任务调度器和存储服务，整体部署复杂，扩展成本较高。相比之下，Serverless 架构更适合将上传完成、转码开始、处理失败、状态同步等环节拆分为独立事件，在对象存储、函数计算和工作流编排的协同下形成完整的媒体处理链路。
本项目采用“前端应用 + 数据库 + 对象存储 + 工作流编排 + 云函数”的组合模式构建视频点播平台。其中，用户侧通过 Web 应用发起上传与播放请求；视频源文件存入对象存储；Step Functions 负责组织多个 Lambda 阶段任务；EventBridge 负责发布流水线阶段事件；处理结果最终回写数据库并反馈到前端页面。该方案体现了 Serverless 架构模块解耦、弹性伸缩、按需执行和事件驱动的典型特点，能够较好适配视频点播业务中“高峰上传、异步处理、结果回显”的场景需求。
2.2 Next.js 16 与 React 19
Next.js 是面向 React 生态的 Web 开发框架，具备路由组织、服务端渲染、接口处理、静态资源管理以及前后端协同开发等能力。React 则通过组件化思想组织界面，实现状态驱动的用户交互。二者结合后，能够兼顾首屏渲染效率、界面复用能力和工程组织规范，适合构建功能较完整的视频平台前端。
本系统前端采用 Next.js 16 与 React 19 实现，项目基于 app 目录组织首页、搜索、播放页、频道页、登录注册页和创作者工作室等页面，并结合 Route Handler 与 Server Action 完成数据获取和业务操作。相比传统前后端完全分离模式，该方案减少了接口重复封装和上下文切换成本，有助于提升开发效率。
两者的组合能够较好满足本系统在交互性、工程化和页面组织方面的要求，也为后续功能扩展提供了良好的前端基础。
2.3 PostgreSQL 与 Prisma
视频点播平台涉及用户、频道、视频、评论、订阅、收藏、播放列表、上传任务、转码任务以及统计数据等多类业务实体，这些数据之间存在较强的结构化关联关系。因此，系统需要具备稳定事务能力、关系建模能力以及良好的查询性能。PostgreSQL 作为成熟的开源关系型数据库，具备事务一致性好、扩展性强、数据类型丰富、查询能力完善等优点，适合用于平台核心业务数据。
本系统选用 PostgreSQL 作为主数据库，并使用 Prisma 作为 ORM 工具实现数据模型定义与数据库访问。Prisma 可以通过统一的 Schema 文件描述实体、枚举、索引和关系约束，再由客户端生成类型安全的数据访问接口，从而降低 SQL 拼写错误和类型不一致问题。在本项目中，数据库层定义了 User、Channel、Video、Comment、Subscription、Playlist、UploadSession、TranscodeJob、VideoAsset、VideoPlaybackEvent、VideoDailyStat、ChannelDailyStat 等核心模型，能够较完整地覆盖点播平台从内容生产到内容消费的业务流程。
其中，Video 模型用于记录视频标题、可见性、处理状态、发布时间、观看次数等核心属性；VideoAsset 用于描述源文件、HLS 主清单、分片资源和缩略图等媒体资产；TranscodeJob 用于追踪队列状态、执行阶段、失败原因和任务完成时间；VideoPlaybackEvent 与日统计表则用于支撑播放行为采集和可视化分析。Prisma 在此基础上还支持基于条件的聚合、分组统计和事务更新，使系统能够较方便地实现频道统计、排行榜、观看时长汇总等功能。
因此，PostgreSQL 提供了可靠的数据持久化基础，Prisma 提供了高效且类型安全的数据访问方式，二者结合能够满足本系统在数据一致性、可维护性和开发效率方面的要求。
 
2.4 AWS相关服务
本系统围绕 AWS Serverless 技术设计媒体处理流程，核心使用对象存储、函数计算、工作流编排和事件总线四类云服务。在开发阶段，项目引入 LocalStack 对相关云服务进行本地仿真，以降低调试成本并提升开发效率；在部署层面，则能够平滑迁移到真实 AWS 环境。
2.4.1 S3 对象存储
Amazon S3 是 AWS 提供的高可用对象存储服务，适合存储图片、视频、日志以及其他非结构化文件。对于视频点播平台来说，原始视频文件体积较大，且转码后还会生成主清单、分片文件与封面图，如果全部存入应用服务器本地磁盘，不仅扩展困难，也不利于多实例部署与统一访问。
本系统使用对象存储保存视频上传和媒体产物管理，并将资源按不同用途划分到多个桶中：原始视频存放于 vod-raw，HLS 输出资源存放于 vod-hls，缩略图与封面图存放于 vod-image。用户上传视频时，系统先由服务端生成预签名上传地址，客户端再直接将 MP4 文件上传至对象存储，从而减少应用服务器带宽压力。转码完成后，HLS 主清单和切片文件继续写入对象存储，播放页面通过主清单地址完成流媒体访问。
2.4.2 Lambda云函数
AWS Lambda 是一种事件驱动的无服务器计算服务，能够在指定事件触发后执行函数逻辑，并按调用量和执行时长进行计费。相较于常驻式转码服务，Lambda 更适合完成步骤清晰、触发明确、可拆分执行的异步处理任务。
本项目将媒体处理流程拆分为多个函数阶段，包括元数据提取、视频转码、封面抽取、结果回写和失败标记等步骤。上传完成后，系统根据视频信息创建转码任务，再通过工作流触发各阶段 Lambda 执行。元数据提取阶段负责将任务状态置为运行中并更新视频处理状态；转码阶段调用 FFmpeg 完成编码、切片和封面截图；收尾阶段负责写入 VideoAsset、更新 Video.thumbnail 并将视频状态改为 READY；失败阶段则在异常发生时将任务修改到 FAILED 状态。
 
2.4.3 Step Functions 工作流编排
视频处理由多个顺序相关、可能失败且需要重试的步骤组成。若仅依靠应用代码手工串联这些步骤，会导致流程控制复杂、异常恢复困难，并增加状态不一致风险。AWS Step Functions 提供了状态机式的工作流编排能力，能够对多步骤任务进行顺序控制、失败捕获、条件分支和重试管理。
本系统使用 Step Functions 对媒体处理流水线进行编排。上传完成后，平台以视频编号、任务编号、输入桶、输出桶、对象键和视频类型等信息作为执行输入启动状态机。状态机依次驱动“提取元数据”“执行转码”“完成回写”等步骤，并在任意阶段异常时统一流转到失败处理逻辑。系统还针对失败调整链路配置重试策略，以提升任务最终状态的一致性，避免前端长期停留在处理中状态。
2.4.4 EventBridge 事件总线 
在媒体流水线运行过程中，仅依靠最终成功或失败结果并不足以支撑前端状态展示和任务监控。平台还需要感知“开始下载源文件”“探测元数据”“执行转码”“上传切片”“上传缩略图”等关键阶段，以向用户提供更细粒度的进度反馈。Amazon EventBridge 提供了事件分发能力，适合在服务之间解耦传递状态变化信息。
本系统在转码 Lambda 的关键节点发布 pipeline.stage 事件，并同步回调内部接口，将当前阶段写入数据库中的 TranscodeJob.pipelineStage 字段。前端工作室页面通过轮询方式获取视频处理状态和当前阶段，从而展示更具可解释性的任务进度。例如，系统可区分任务当前处于“下载源文件”“探测视频信息”还是“上传分片”阶段，而不是简单地显示“处理中”。
2.5 FFmpeg 与 HLS 流媒体技术
FFmpeg 是广泛应用于多媒体处理领域的开源工具集，支持音视频转码、格式转换、封面截取、分片封装和元数据探测等功能。HLS 是一种基于 HTTP 的流媒体传输协议，其核心思想是将完整视频切分为多个较短片段，并通过 m3u8 清单文件组织播放顺序，使客户端能够以分段方式加载媒体内容。
在视频点播业务中，直接播放用户上传的原始 MP4 文件往往存在兼容性差、首帧时间长、断点恢复能力弱等问题。相比之下，HLS 方案能够更好地适配浏览器与移动端播放器，同时便于与 CDN、对象存储和权限控制机制配合。播放器只需先请求主清单，再按需拉取后续分片，即可实现更平滑的在线播放。
本系统在转码环节使用 FFmpeg 对用户上传的 MP4 文件进行处理，完成视频探测、HLS 切片、主清单生成和缩略图抽取等工作。处理完成后，系统将 master.m3u8 与 seg_*.ts 切片文件写入对象存储，并将封面图保存到独立的图片桶中。播放页面则通过 HLS 地址向播放器提供媒体源，实现在线视频播放。对于长视频场景，该方案能够在保证播放兼容性的同时，将媒体处理流程与页面播放流程有效分离。
2.6 Better Auth 认证机制
视频点播平台不仅包含公开浏览能力，还涉及用户注册登录、创作者工作室、评论互动、收藏夹、播放列表和频道管理等功能，因此必须建立稳定的身份认证与权限控制机制。认证方案既要支持基础的账号登录，也要兼顾第三方登录扩展能力，并能够方便地与前端页面和数据库模型整合。
本系统采用 Better Auth 实现认证机制，并结合 Prisma 适配器将用户、会话、账号绑定和校验信息持久化到 PostgreSQL 中。系统已支持邮箱密码登录，同时预留 GitHub 与 Google 第三方登录方式。认证完成后，平台基于会话信息识别当前用户身份，并在视频编辑、播放列表管理、评论操作、订阅、工作室访问以及上传转码任务控制等场景中进行权限校验。

同时，项目在开发阶段可借助 LocalStack 对对象存储、函数计算、工作流和事件总线进行本地仿真，能够降低联调难度并验证关键链路。因此，该系统在技术层面具有明确的实现基础和较高的可行性。
2.7.2 经济可行性 
Serverless 架构的优势在于按需使用资源。对于中小规模视频平台而言，若直接长期维护固定规模的转码服务器和调度服务，容易造成前期投入偏高和资源闲置；而基于 Serverless 的处理链路可以随任务触发动态运行，成本结构更符合渐进式建设需求。
同时，本项目采用对象存储保存媒体文件，并通过 LocalStack 完成开发阶段的大部分本地联调，能够进一步降低试错成本。因此，该方案具备较好的经济可行性。
2.7.3 运行和维护可行性 
Serverless 架构将大量基础设施职责交由云平台承担，系统维护重点更多转向业务逻辑、任务监控和异常恢复。相较于传统转码集群方案，该方案无需长期维护独立的转码服务器池和复杂的分布式调度组件，维护压力相对较小。
此外，平台通过状态回写、失败调整和任务重试等机制增强链路的可观测性与可恢复性，也便于后续围绕推荐、审核或多清晰度转码等能力继续扩展。因此，该系统在运行管理与后续维护方面具备较好的可行性。
结合本章节讨论，本系统所采用的技术路线能够较好匹配视频点播平台的业务特点，并在技术实现、成本投入和运行维护三个方面具有较强的可行性。

第4章	系统设计
视频点播平台与一般信息管理系统相比，既包含账号、内容、评论、播放列表和统计分析等常见业务模块，又包含视频上传、异步转码、HLS 分发和任务状态回写等媒体处理链路。因此，系统设计既要考虑页面组织、服务分层和数据库结构，也要关注媒体流水线的职责拆分、状态一致性和部署方式。
本章围绕系统总体架构、业务流程、功能模块、数据库、接口以及部署与本地仿真环境展开设计说明。相关设计均以项目当前实现为基础，强调前端页面、服务端逻辑、数据库模型与 Serverless 媒体处理流程之间的协同关系。
4.1 系统总体架构设计
系统总体架构决定了功能模块之间的关系边界，也决定了后续实现是否具备清晰的扩展路径。结合本项目技术栈与业务特点，平台采用“统一 Web 应用 + 关系数据库 + 对象存储 + 工作流编排 + 云函数处理”的总体模式。这样的组合既保留了 Next.js 全栈工程的开发效率，又能够将大文件上传和异步媒体处理从常规页面请求中解耦出来。
4.1.1 系统整体架构
系统由用户浏览器、Next.js 应用层、PostgreSQL 数据层以及基于 LocalStack 仿真的 AWS Serverless 媒体处理层组成。普通页面访问、评论互动、播放列表管理和统计查询等请求主要由 Next.js 应用层处理；结构化业务数据由 PostgreSQL 负责存储，并通过 Prisma 提供类型安全的数据访问能力；视频源文件、HLS 产物和缩略图则分别保存在不同的对象存储桶中；上传后的媒体处理任务由 Step Functions 组织多个 Lambda 阶段执行，并通过内部回调接口把处理结果写回数据库。

4.2 系统业务流程设计
系统业务流程设计的重点在于说明页面请求、数据库状态和媒体处理链路之间如何形成流程。结合本项目实现，平台的核心流程可概括为用户浏览与播放、视频上传与处理、评论互动与收藏、统计采集与展示，以及媒体流水线内部时序五个方面。
4.2.1 用户浏览与播放流程
用户浏览与播放流程从首页或搜索页开始。浏览器访问首页时，Next.js 服务端从数据库读取公开视频列表，并将结果渲染为视频卡片。用户点击某条视频后进入播放页，页面通过短码查询视频详情、频道信息、推荐内容和评论区数据，并根据视频可见性、处理状态和当前登录身份决定是否允许访问。
若视频已处于可播放状态，播放器会读取 HLS 主清单地址。在本地开发环境下，播放请求经由 /api/hls/[...objectKey] 代理到对象存储；在配置 CDN 域名的情况下，也可以直接经由 CDN 域名访问媒体资源。播放过程中，前端持续向 /api/videos/[shortCode]/playback-events 上报播放事件，系统将事件写入 VideoPlaybackEvent 表，为后续统计分析提供原始数据。

4.2.2 视频上传与处理流程

4.2.3 评论互动与收藏流程
评论互动与收藏流程都建立在用户登录状态之上。用户在播放页提交评论时，请求先到达 Route Handler，再由业务服务层完成登录态校验、视频存在性校验和内容合法性校验，最终写入 Comment 表。回复评论的过程与之类似，只是在写入时附带 parentId 以建立评论层级关系。评论点赞、视频点赞和频道订阅等行为均采用相似的模式：前端发起操作，服务端执行鉴权与资源检查，数据库完成写入，相关计数通过触发器自动维护。
收藏夹、稍后再看以及自定义播放列表的处理也遵循这一思路。系统默认提供“收藏夹”和“稍后再看”两类系统播放列表，用户可以在播放页快速保存视频；若用户需要更强的组织能力，则可在工作室中创建和维护自定义播放列表。列表项通过 PlaylistItem.position 字段保持顺序一致性，从而支持连续播放和拖拽排序等交互。

4.2.4 统计数据采集与展示流程
统计分析流程由“原始事件采集”和“日级统计展示”两个阶段组成。原始事件采集主要依赖播放器在播放过程中持续上报的行为事件，这些事件被写入 VideoPlaybackEvent 表。与此同时，评论、点赞和订阅等互动数据直接写入对应业务表，并由数据库触发器维护累计计数字段。
在统计汇总阶段，数据库通过 sp_rollup_daily_stats 存储过程按日期范围聚合 VideoPlaybackEvent、VideoReaction、Comment、Subscription 和 Video 等数据，生成 VideoDailyStat 与 ChannelDailyStat 两张日级统计表。工作室中的统计页面读取这些结果，构建频道趋势、视频排行榜、类型分布和单视频明细视图。由于统计查询直接面向日级汇总数据，因此在页面展示时能够避免频繁扫描大量原始事件记录。

4.2.5 媒体处理流水线时序设计
媒体处理流水线时序关注任务内部如何推进。状态机启动后，extract-metadata 负责将任务状态更新为 RUNNING、视频状态更新为 PROCESSING；transcode 负责从原始桶下载视频、执行 FFmpeg 转码、上传 HLS 切片和缩略图，并在关键节点发布阶段事件；finalize 负责生成 VideoAsset 记录、更新 Video.thumbnail 和 Video.readyAt；若任一阶段异常，则统一进入 mark-failed，完成失败状态写入。对于长时间停留在 QUEUED 或 RUNNING 的任务，系统还提供 reconcile-stale 维护接口进行对账与纠错。

4.3 功能模块设计
4.3.1首页与搜索模块设计
首页与搜索模块承担平台内容发现职责。首页以公开视频为展示对象，通过视频卡片呈现标题、封面、播放量和发布时间等基础信息，并区分长视频与短视频两类内容。为适应内容持续增长的场景，视频列表采用游标式分页和增量加载方式，减少一次性拉取全部数据带来的压力。
搜索模块在数据来源上与首页保持统一，仍然只面向已公开且处理完成的视频进行检索。检索条件主要围绕视频标题、描述和频道名称展开，返回结果按照内容相关性与热度进行组织。这样设计的好处在于，首页与搜索共享同一套内容访问约束，能够避免草稿、私有或尚未完成转码的视频误入公开展示范围。
4.3.2视频播放与推荐模块设计
播放模块由播放器、视频信息区、频道信息区、评论区和推荐区共同构成。播放源优先使用已生成的 HLS 主清单地址，在本地仿真环境下由 HLS 代理接口转发到对象存储，在具备 CDN 域名配置时则可直接切换到外部域名访问。页面在服务端装配视频详情与频道信息时，会同步判断当前用户是否为视频所有者，以及当前视频是否处于公开、私有、草稿或处理中状态。
推荐模块以当前视频为参照，从公开视频集合中选择其他可浏览内容作为侧边推荐列表。若视频处于播放列表上下文中，页面还可以展示对应的播放列表面板，使用户在当前主题内容下继续顺序观看。通过把播放、推荐和播放列表组合到同一页面中，系统能够更好地支撑内容连续消费。
4.3.3评论互动模块设计
评论互动模块围绕“可分页的主评论 + 可递增加载的回复”进行组织。主评论支持按热度和最新时间排序, 回复评论则通过父子结构与主评论关联, 从而构成层级式讨论区。为了避免前端承担复杂的聚合逻辑, 评论列表查询由服务层统一完成, 并在返回时附带当前用户的历史反应状态, 便于页面直接渲染点赞或点踩按钮状态。
点赞、点踩和评论反应等互动行为采用“接口提交 + 数据表写入 + 触发器维护计数”的模式。这样既保留了交互操作的实时性, 也把点赞数、评论数和回复数的维护放回数据库层, 减少页面层和服务层手工维护计数字段的负担。
4.3.4频道与订阅模块设计
频道模块将创作者与其公开视频集合绑定为一个统一的内容空间。每个注册用户在首次进入上传场景时，系统会自动为其创建唯一频道，并将视频内容与该频道关联。频道页面不仅展示频道基础信息和公开视频列表，还承担了创作者形象展示与用户关注关系保存的作用。
订阅功能围绕 Subscription 实体展开。用户在频道页或播放页中均可触发订阅与取消订阅操作，服务端会校验频道归属关系，防止用户订阅自己，并由数据库触发器自动维护频道订阅人数。订阅关系既服务于前台展示，也为后续统计分析中的净增订阅指标提供基础。
4.3.5收藏夹与播放列表模块设计
播放列表模块由系统默认列表和用户自定义列表两部分组成。系统默认提供“稍后再看”和“收藏夹”两类播放列表，便于用户在播放页中一键完成快速保存；自定义播放列表则用于支持更细粒度的内容组织。所有播放列表都归属于当前用户，并通过 PlaylistItem 与视频建立多对多关系。
列表项设计中，position 字段用于保持播放顺序，系统在添加、删除和重排时都会同步更新位置值，以保证列表顺序一致性。对于公开视频列表，系统支持在播放页中直接展示面板，从而形成“当前视频 + 列表上下文”的顺序消费体验。
4.3.6创作者工作室模块设计
工作室模块是平台后台治理能力的核心。该模块包含内容列表、单视频详情、上传对话框、播放列表管理和统计分析入口等多个子界面，用于把创作者在内容生产、内容维护和数据复盘中的操作集中到统一空间。用户进入工作室后，可以查看自己上传的视频列表、搜索视频、编辑视频基础信息、删除视频、切换可见性以及调整封面图。
考虑到媒体处理属于异步任务，工作室并不只展示静态数据，而是同时承担状态追踪职责。内容列表页和单视频详情页都可以读取 processingStatus、pipelineStage 和 jobError 等任务信息；当任务失败时，用户可以通过重试和取消接口发起后续操作。工作室的设计重点不只是“能上传”，而是为创作者提供从上传、处理到发布、分析的完整流程。
4.3.7视频处理流水线模块设计
视频处理流水线模块由上传会话、转码任务、对象存储资源和状态机编排共同构成。上传会话用于描述原始视频的上传过程，转码任务用于描述上传完成后的异步处理过程，视频资产用于保存最终可播放资源和缩略图信息。通过把这三个对象拆开建模，系统能够分别追踪“文件是否已上传”“任务是否已执行”“产物是否已生成”这三种不同状态。
流水线模块在执行路径上保持清晰的阶段边界。状态机只负责顺序控制和失败捕获，不直接负责业务数据；具体数据变更则由各阶段 Lambda 通过内部回调接口写回应用数据库。这样的设计可以避免 Step Functions 直接访问业务数据库带来的耦合风险，也使媒体处理逻辑保持在相对独立的执行环境中。
4.3.8统计分析模块设计
统计分析模块面向创作者提供频道视图与单视频视图两类入口。频道视图重点展示近 30 天观看次数、观看时长、净增订阅和发布数量等总体指标，并通过折线图、环形图和榜单表反映内容结构与热门视频表现；单视频视图则聚焦于某条视频的观看趋势、独立观众、互动增量和累计摘要，以便创作者从宏观数据进一步深入到具体内容表现。
在数据来源上，统计页并不直接计算原始事件，而是以 VideoDailyStat 和 ChannelDailyStat 为主要读取对象。这样既能够控制查询复杂度，也使统计口径在页面之间保持一致。统计模块本质上不是独立的业务系统，而是前台播放行为和后台运营分析之间的桥梁。
4.3.9数据采集与统计分析机制设计
为了使统计模块具备可靠数据来源，系统在设计上采用“实时采集原始事件、离线汇总日级统计”的双层机制。实时层由播放器在观看过程中持续上报播放事件，服务端将其写入 VideoPlaybackEvent 表；互动层则由评论、点赞和订阅等业务写操作直接更新业务表，并由数据库触发器维护累计计数。通过这种方式，系统可以同时获得足够细粒度的原始行为记录和即时更新的累计字段。
统计汇总层通过 sp_rollup_daily_stats 存储过程把原始事件转换为日级统计结果。该过程按日期范围聚合播放次数、独立观众、观看时长、评论增长、点赞增长和订阅增长，并把结果分别写入视频和频道统计表。相比直接在页面层扫描原始事件表，这一设计更适合长期积累后的数据量，也更符合运营分析场景对统计口径稳定性的要求。
4.3.10异常恢复与任务一致性设计
媒体处理链路天然包含失败风险，因此异常恢复与任务一致性是系统设计中的重点内容。状态机在 Transcode 和 MarkFailed 等环节配置了重试策略，用于处理临时性错误；finalize 在写入 VideoAsset 时先删除旧的 HLS_MASTER 和 THUMBNAIL 记录，再创建新资产，以降低重试场景下的重复写入问题；cancelVideoJob 则允许创作者主动终止排队中或执行中的任务，并将任务状态修改到 CANCELED 或 FAILED 状态。
对于更隐蔽的一类异常，即任务停留在 QUEUED 或 RUNNING 但实际上已经失效的“僵尸任务”，系统提供了内部 reconcile-stale 接口进行对账与修正。该接口会识别超出阈值的陈旧任务，并在确认不存在其他活跃任务后将其变为到失败状态。通过“状态机 Catch 分支 + 任务取消 + 对账纠错”的组合设计，系统能够在较长运行周期内维持较好的状态一致性。

第5章	系统实现
本章将从页面组织、接口处理、服务层封装、数据库状态维护以及 Serverless 媒体处理链路五个角度，对用户认证、内容浏览、视频在线播放、评论互动、播放列表、视频上传、创作者工作室和统计分析等功能进行展开说明。
本系统基于 Next.js 16 的 App Router 组织页面与接口，前端页面主要位于 app/ 目录下，接口通过 app/api/ 下的 Route Handler 提供，核心业务逻辑集中在 lib/server/ 中封装，数据存取通过 Prisma 访问 PostgreSQL，媒体处理链路则由 lib/localstack.ts、内部回调接口以及本地仿真的 Step Functions、Lambda 和 S3 共同完成。通过这种实现方式，系统形成了“统一 Web 应用，数据库业务，对象存储，状态机驱动异步处理”的完整工程流程。
5.1 用户认证与权限控制实现
用户认证模块采用 Better Auth 与 Prisma 适配器实现。系统在 lib/auth.ts 中完成认证实例配置，将 user、session、account 和 verification 等认证相关表与 PostgreSQL 关联，并开启邮箱密码登录方式，同时预留 GitHub 与 Google 第三方登录能力。app/api/auth/[...all]/route.ts 将 Better Auth 封装为统一认证入口，从而承担注册、登录、获取会话和退出登录等请求。登录页与注册页分别通过 app/login/page.tsx 和 app/signup/page.tsx 提供，客户端表单组件 components/login-form.tsx 与 components/signup-form.tsx 则负责收集用户输入并调用认证接口。
系统通过 lib/server/auth-session.ts 提供 getOptionalUserId() 和 requireUserId() 两个统一入口。对于首页、搜索页和公开播放页等匿名可访问场景，服务层调用 getOptionalUserId() 读取可选会话，以决定是否返回用户个性化状态；对于评论发布、频道订阅、播放列表管理、视频上传、工作室访问和统计分析等必须登录的场景，则通过 requireUserId() 强制校验身份，未登录时直接拦截请求。这种实现方式使页面权限、接口权限与服务层权限保持一致，避免了逻辑分散带来的遗漏问题。
除基础登录态之外，系统还实现了用户偏好设置持久化。app/api/settings/route.ts 提供主题偏好读取和更新接口，lib/server/settings.ts 将数据写入 user_settings 表，hooks/use-settings.ts 则在客户端通过 SWR 与本地缓存同步主题配置，保证登录用户在不同页面中能够保持统一的界面偏好。

5.2 首页浏览与搜索功能实现
首页浏览与搜索功能主要围绕公开视频列表查询展开。首页入口为 app/page.tsx，页面通过 VideoGallery 组件组织视频卡片流，并使用 BrowseShell 统一页面布局。视频列表数据由 app/api/videos/route.ts 提供，服务层调用 lib/server/videos.ts 中的 getVideos() 方法完成分页查询。该方法在数据库层限定 deletedAt 为空、visibility 为 PUBLIC、processingStatus 为 READY 的视频才能进入公开列表，同时根据 LONG 与 SHORT 两类内容分别返回游标分页结果。这一实现保证了首页不会提前暴露草稿、私有视频或尚未转码完成的视频。
搜索页入口为 app/search/page.tsx。页面从查询参数中读取关键词后，调用 searchVideos() 按视频标题、简介和频道名称进行模糊匹配，并按照观看量和发布时间排序结果。由于搜索逻辑与首页共享相同的公开视频过滤条件，因此系统能够在“首页推荐”和“关键词检索”之间保持一致的内容访问边界。对于用户而言，首页负责内容发现，搜索页负责目标定位，两者最终都归结为对公开视频资源的安全读取。
首页和搜索页共用视频网格组件，视频卡片统一展示缩略图、标题、频道作者、播放量和发布时间等信息；在数据获取上，则通过接口层和服务层分离的方式提升可维护性。后续若需要增加分区推荐、排序切换或瀑布流加载，也可以在现有实现上继续扩展。
5.3 视频播放与推荐功能实现
视频播放页位于 app/watch/[shortCode]/page.tsx，是系统前台消费链路的核心页面。页面首次加载时会并发调用 getVideoInfo() 与 getWatchSidebarData() 两个服务函数，分别获取视频基础信息、频道信息、当前用户互动状态以及右侧播放列表上下文。getVideoInfo() 中实现了较完整的访问控制逻辑：对于公开和不公开视频，非作者只有在视频转码完成后才能访问；对于私有和草稿视频，则只有作者本人能够查看，其他用户会被重定向到登录页或直接拒绝访问。通过这种方式，系统在播放页层面实现了内容可见性和处理状态的双重控制。
视频资源地址优先使用已配置的 CDN 域名；若开发环境未配置 CDN，则退回到 /api/hls/[...objectKey] 代理接口读取 HLS 清单和分片。播放器组件 VideoPlayer 基于 HLS 主清单地址进行播放，视频详情区 VideoInfo 展示标题、频道信息、点赞、收藏和订阅等操作入口，评论区 CommentArea 用于展示和提交评论，侧边栏 RecommendationList 负责推荐其他公开视频。推荐数据由 getRecommendation() 生成，其内部通过随机查询从公开视频集合中选取候选内容，保证当前页面可以形成连续观看体验。
为了支撑后续统计分析，系统在播放过程中还通过 /api/videos/[shortCode]/playback-events 接口上报播放行为事件。recordPlaybackEvent() 会将播放开始、播放进度、暂停、恢复、拖动和结束等行为写入 VideoPlaybackEvent 表，并保存会话标识、播放位置、观看时长增量和浏览器环境信息，为后续的日级统计汇总提供原始数据来源。

5.4 评论互动功能实现
评论互动模块以播放页为主要入口，其后端实现集中在 lib/server/comments.ts 中。系统通过 app/api/videos/[shortCode]/comments/route.ts 提供评论列表查询与评论发布接口，通过 app/api/comments/[commentId]/replies/route.ts 提供回复分页与回复新增接口，通过 app/api/comments/[commentId]/reaction/route.ts 提供评论点赞和点踩接口。主评论查询支持“按热度排序”和“按时间排序”两种模式，其中热门排序以 likesCount 和创建时间作为联合游标条件，最新排序则以时间和主键构造分页游标。这种实现方式保证了评论区在数据规模增长后仍然具备可扩展的分页能力。
在前端交互方面，hooks/use-comments.ts 与 hooks/use-replies.ts 基于 SWR 实现评论和回复的增量加载，并在新增评论、删除评论、更新评论和切换点赞状态时执行乐观更新，从而减少用户等待感。评论内容提交前会进行非空校验，服务端还会校验视频或父评论是否存在。对于未登录用户，服务层在进入写操作前会直接触发身份校验，确保评论区写入能力只对登录用户开放。
评论模块中的计数字段维护并不是在应用层手工累加，而是交由数据库触发器完成。prisma/triggers.core.sql 中定义了评论计数、评论回复数以及评论点赞数维护逻辑：当评论新增或删除时，自动更新 Video.commentsCount 与父评论的 repliesCount；当评论互动表发生变化时，自动更新 Comment.likesCount 与 Comment.dislikesCount。这种实现降低了应用层并发写入下出现计数不一致的风险。

5.5 频道展示、订阅与用户内容页实现
频道页位于 app/channel/[name]/page.tsx，其数据由 getChannelPageData() 统一装配。该函数首先按频道名称读取频道基础信息和创作者资料，再查询频道下所有公开且已处理完成的视频，同时统计公开视频数量和累计观看量。页面在视觉上将频道横幅、创作者头像、订阅人数、加入时间和最新视频列表整合在一起，使频道既承担内容聚合入口，也承担创作者展示页的作用。

订阅功能通过 app/api/channels/[channelId]/subscription/route.ts 暴露，底层调用 toggleSubscribe() 对 Subscription 表进行新增或删除操作。系统在实现中显式禁止用户订阅自己的频道，并在数据库层通过触发器自动维护 Channel.subscribersCount。这样一来，频道页、播放页中的订阅按钮，以及统计页中的订阅增长分析，都可以共享同一组订阅关系数据。
除频道页之外，系统还提供了围绕当前用户的内容页。app/history/page.tsx 通过 getHistoryVideos() 展示观看历史，读取 VideoPlaybackEvent 中最近一次观看记录；app/saved/page.tsx 则基于收藏夹和稍后再看两类系统播放列表，展示用户已保存的视频集合。相比单纯的频道展示，这两类页面体现了系统已经从“内容发布”扩展到“内容留存与回访”的用户内容组织能力。
5.6 收藏夹与播放列表功能实现
播放列表模块由系统播放列表和自定义播放列表两部分组成。系统播放列表包括“稍后再看”和“收藏夹”，其核心逻辑由 toggleSystemPlaylistVideo() 实现。当用户在播放页点击保存按钮时，系统首先检查目标视频是否具备可保存条件：若视频属于当前用户，则允许直接保存；若视频属于他人，则必须满足公开视频或不公开视频且转码完成的条件。之后系统在事务中自动创建或复用对应的系统播放列表，并向 PlaylistItem 表中添加或移除记录，同时维护 position 字段和列表更新时间。
自定义播放列表相关功能位于工作室接口中，由 listUserPlaylists()、createPlaylist()、updatePlaylist()、deletePlaylist() 与 listPlaylistItems() 等服务函数提供支撑。播放列表默认只允许所有者维护，且通过 systemKey 区分系统列表与自定义列表，防止用户误修改系统默认结构。列表项通过 playlistId + position 的唯一约束保持顺序稳定，当视频被加入或移出列表时，系统会自动调整后续项的位置编号，从而保证连续播放和顺序浏览的正确性。
在前台页面上，播放页右侧可以读取当前视频所属的播放列表并展示 PlaylistPanel，用户也可以通过收藏页和稍后再看页回看已保存内容；在后台页面上，创作者可在工作室中创建和管理自定义播放列表。至此，系统不仅支持“看视频”，也支持“组织视频”和“按主题继续看”。
5.7 视频上传与媒体处理流水线实现
视频上传与媒体处理流水线是本系统最具工程特点的部分。与普通内容管理系统只处理表单文本不同，本系统需要完成视频草稿创建、对象存储直传、转码任务入队、状态机调度、HLS 切片、封面抽取、任务状态回写以及失败恢复等多个步骤。整个流程由上传接口、数据库模型、LocalStack 仿真的 S3/Step Functions/Lambda 以及内部回调接口共同组成。
5.7.1 上传会话与对象存储实现
上传入口由api/uploads/video-url/route.ts 提供，底层调用 getVideoUploadUrl()。当创作者选择视频文件后，系统首先调用 createUploadVideoDraft() 创建视频草稿，并为其生成唯一短码；若当前用户尚未拥有频道，ensureChannelForUser() 会自动创建频道记录，将视频与创作者频道关联起来。随后，系统依据视频短码生成对象存储键 {shortCode}/source.mp4，调用 createUploadPresignedUrl() 生成预签名上传地址，并写入 UploadSession 记录。
前端上传逻辑由 use-video-upload.ts 管理。该 Hook 使用 XMLHttpRequest 直接向对象存储执行 PUT 请求，并通过上传进度事件实时更新状态，从而避免应用服务器承担大文件中转压力。上传完成后，前端再调用 /api/videos 通知服务端启动后续媒体处理流程。通过“先申请上传地址，再直传对象存储，最后创建任务”的设计，系统将大文件传输与业务状态创建解耦，显著降低了 Web 应用在上传场景下的带宽压力。
5.7.2 元数据提取实现
上传完成后，createVideo() 根据已完成的 UploadSession 创建 TranscodeJob 记录，并调用 startTranscodeExecution() 启动状态机。状态机启动后首先进入元数据提取阶段，该阶段对应内部回调接口 /api/internal/vod/update-metadata。该接口在收到 jobId 和 videoId 后，通过事务将转码任务状态更新为 RUNNING，将视频状态更新为 PROCESSING，同时记录任务启动时间与尝试次数。
虽然元数据的具体探测工作由 Lambda 侧结合 FFprobe 和 FFmpeg 完成，但在应用侧，这一阶段最核心的职责是建立“任务已开始执行”的一致性状态，并为后续时长、分辨率和封面等元信息回写预留字段。工作室页面中的处理中提示，正是依赖这一阶段写入的 processingStatus 与 TranscodeJob.status 字段才能及时更新。
5.7.3 转码与 HLS 切片实现
转码与 HLS 切片阶段是整个流水线的核心执行环节。系统通过 FFmpeg 将原始 MP4 视频转换为 master.m3u8 及分片文件，并将产物上传至 vod-hls 桶。为了增强处理过程的可观测性，Lambda 在关键阶段会回调 /api/internal/vod/stage，将 job_started、downloading、probing、transcoding、uploading_segments、thumbnail_extracting 等阶段标识写入 TranscodeJob.pipelineStage 字段。
这一设计使前端不必依赖难以稳定表达的百分比进度，而是可以展示更贴近实际处理链路的阶段提示，例如“正在探测视频信息”“正在转码切片”“正在上传媒体分片”等。对于视频在线播放而言，当 master.m3u8 上传完成并在最终阶段回写后，播放页即可通过对象存储代理接口或 CDN 域名读取 HLS 资源。
5.7.4 封面抽取与状态回写实现
在转码阶段完成后，状态机进入收尾阶段，对应内部接口 api/internal/vod/finalize。该接口会根据 Lambda 回传的信息统一完成三类数据写入。第一，更新 TranscodeJob 状态为 SUCCEEDED，清空阶段标识并记录结束时间；第二，更新 Video 状态为 READY，写入 readyAt、视频时长以及缩略图访问地址；第三，向 VideoAsset 表写入 HLS_MASTER 资产记录，并在存在封面图时写入 THUMBNAIL 资产记录。
在封面图地址构建方面，系统支持两种访问方式：若配置了图片 CDN 域名，则使用 https://域名/对象键 的形式返回；若处于本地开发环境，则退回到 LocalStack 的对象访问地址。为了保证重试场景下的数据幂等性，finalize 在写入新的 HLS_MASTER 和 THUMBNAIL 资产前，会先删除旧记录，避免同一视频在重复执行成功后出现资产重复的问题。
5.7.5 异常处理与任务纠错实现
媒体处理链路天然存在转码失败、执行超时、用户主动取消和状态机异常中断等风险。为此，系统提供了多层次的异常处理机制。首先，状态机异常会统一回调 /internal/vod/mark-failed，由该接口将 TranscodeJob 和 Video 改为 FAILED 状态，并记录错误信息；其次，创作者可以通过 /api/studio/videos/[shortCode]/retry 和 /api/studio/videos/[shortCode]/cancel 发起重试和取消操作，其中 retryVideoJob() 会复用历史任务输入重新创建任务，cancelVideoJob() 则会停止状态机执行并将本地任务标记结束。
此外，系统还实现了僵尸任务纠错机制。/api/internal/vod/reconcile-stale 会扫描长时间停留在 QUEUED 或 RUNNING 状态的任务，在确认不存在其他活跃任务后，将这些异常记录统一修正为 FAILED，并同步修正视频的处理状态。这样可以防止工作室页面长期显示“处理中”而实际任务早已失效，从而提升系统整体的一致性和可维护性。
5.8 创作者工作室与内容管理实现
创作者工作室承担系统后台管理入口的职责，其页面主要位于 app/studio/ 目录下。app/studio/contents/page.tsx 通过 ContentsPanel 展示当前用户的视频内容列表，app/studio/contents/video/[id]/page.tsx 则基于 getVideoDetails() 提供单视频编辑页，用于维护标题、简介、封面、可见性和质量信息。服务层中的 listUserVideos()、editVideo()、deleteVideo()、getProcessingStatuses() 和 getPipelineStatus() 等方法，分别支撑工作室列表查询、视频编辑、软删除以及任务状态轮询。
工作室实现的关键点在于它并不是简单的静态后台，而是一个持续感知媒体任务状态的动态控制台。上传文件后，useVideoUpload() 会进入轮询状态，周期性读取 /api/videos/[shortCode]/pipeline-status 返回的处理结果，并将上传、提交任务、转码中、完成或失败等状态同步到界面中。当任务失败时，工作室允许用户直接发起重试或取消；当任务成功后，编辑表单能够继续维护视频基础信息并进入发布阶段。
除了视频内容管理外，工作室还集成了自定义播放列表管理能力和统计分析入口。系统将创作者在内容生产、列表组织和数据查看中的高频操作集中到统一工作区内，从而形成从“上传视频”到“管理视频”再到“分析视频”的流程体验。
5.9 统计分析模块实现
统计分析模块面向创作者提供频道级和单视频级两类分析能力。频道统计页位于 app/studio/stat/page.tsx，其数据由 getStatPageData() 提供；单视频分析页位于 app/studio/stat/[shortCode]/page.tsx，其数据由 getVideoAnalyticsPageData() 提供。页面通过多个统计卡片、趋势图、订阅流图、内容类型环形图、榜单表格和明细探索组件，将聚合后的数据进行可视化展示。
在数据来源上，统计模块并不直接对原始事件表进行大范围实时聚合，而是采用“原始行为记录 + 日级汇总结果”的双层实现。播放页上报的行为事件被写入 VideoPlaybackEvent 表，评论、点赞和订阅等业务数据则通过业务表和触发器持续维护累计状态；随后，prisma/rollup.daily.sql 中定义的 sp_rollup_daily_stats 存储过程会按照日期范围，将播放行为、互动行为和发布行为汇总到 VideoDailyStat 与 ChannelDailyStat 两张表中。这样一来，统计页只需读取相对稳定的日级汇总数据，即可快速生成近 7 天、近 14 天或近 30 天的趋势结果。
频道统计页主要展示 30 天观看次数、观看时长、净增订阅和发布视频数，并给出频道整体趋势与视频榜单；单视频分析页则进一步展示某条视频的累计观看、独立观众、观看时长和互动增量。这一模块标志着系统不再停留在基础点播和上传管理层面，而是已经具备面向创作者运营分析的数据支撑能力。

结　论
本文设计并实现了一个基于 AWS Serverless 架构的视频点播平台，采用 Next.js、React、PostgreSQL 与 Prisma 构建前后端一体化应用，结合 Lambda、Step Functions 与 S3 实现异步媒体处理流水线，并引入 LocalStack 在开发阶段对云端资源进行本地仿真。系统覆盖了用户认证、视频上传与转码、在线播放、评论互动、频道订阅及创作者工作室等核心功能，形成了完整的业务流程。
在技术实现上，有两点值得记录。首先是流水线的异常恢复设计：由于 Lambda 存在超时限制，Step Functions 各步骤之间的状态传递需要显式管理，一旦某个处理环节失败，必须确保任务状态能够调整到可观测、可重试的结果，而非停滞于中间状态。这一机制的设计过程加深了对 Serverless 编程模型约束的理解。其次是 LocalStack 的引入：本地仿真环境虽无法完全还原真实 AWS 的行为细节，但在开发验证阶段有效缩短了反馈周期，降低了云端调试的成本。
本方案适用于中小规模团队的新业务建设或教学实验场景，能够以较低的运维成本跑通完整的视频处理链路。不足之处在于：测试覆盖尚不完整，性能未经系统性量化验证，推荐、内容审核与多码率自适应转码等功能亦有待扩展，真实云环境下的稳定性仍需进一步验证。
