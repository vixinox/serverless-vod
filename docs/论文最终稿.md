基于AWS Serverless的视频点播平台的设计与实现
摘　要
在线视频业务逐渐成熟，目前中小规模的视频点播的主要痛点是存储、转码与分发等环节，分布式架构成本高昂且运维复杂，还有资源利用不均等问题。针对这个场景，本文设计并实现了一套基于 AWS Serverless 架构的视频点播平台。采用 Next.js 16 与 React 19 构建前端，使用 PostgreSQL 与 Prisma 完成数据建模和持久化，并借助 Better Auth 实现用户认证与权限控制。媒体处理部分通过对象存储管理视频文件，利用 Step Functions 编排 Lambda 完成元数据提取、FFmpeg 转码、HLS 切片、封面抽取与异步回写，并结合 EventBridge 实现媒体处理链路中的事件传递。前端通过轮询方式获取任务状态，实现处理进度展示。系统实现了视频上传、处理、发布、播放以及评论、收藏、播放列表和统计分析等基本功能。结果表明，系统成功做到了预期功能，各模块运行稳定。测试结果验证了 AWS Serverless 架构在处理异步转码与并发请求时的有效性，为中小规模场景的搭建提供了可行的工程实践方案。

关键词：Serverless；视频点播平台；Next.js；云函数；对象存储；工作流编排


 
Design and Implementation of a Video-on-Demand Platform Based on AWS Serverless Architecture

Abstract
As online video services continue to mature, small- and medium-scale video-on-demand (VOD) platforms increasingly face practical challenges in storage, transcoding, and content distribution. Traditional distributed architectures often require high deployment and maintenance costs, while also suffering from operational complexity and uneven resource utilization. To address these issues, this paper designs and implements a video-on-demand platform based on the AWS Serverless architecture.
The platform adopts Next.js 16 and React 19 for the frontend, PostgreSQL and Prisma for data modeling and persistence, and Better Auth for user authentication and access control. In the media-processing workflow, video files are managed through object storage, while AWS Step Functions orchestrate Lambda functions to complete metadata extraction, FFmpeg transcoding, HLS segmentation, thumbnail generation, and asynchronous status write-back. EventBridge is used for event delivery within the processing pipeline, and the frontend obtains task progress through status polling.
The implemented system supports core functions including video uploading, processing, publishing, playback, commenting, favorites, playlists, and statistical analysis. Test results show that the platform achieves the expected functional goals and operates reliably in the current test environment. The testing results further demonstrate the feasibility and effectiveness of the AWS Serverless architecture for handling asynchronous transcoding tasks and concurrent access requests, providing a practical engineering solution for small- and medium-scale VOD scenarios.

Key Words: AWS Serverless; Video-on-Demand Platform; Next.js; Lambda; Object Storage; Workflow Orchestration

第1章	绪论
在线视频已成为互联网业务的重要组成。视频平台、在线教育、企业培训和活动回看系统，视频点播都已经成为一个必要的基本需求。视频业务的主要复杂度体现在数据处理和分发方式，具体为上传、转码、存储、分发和播放。这些对系统架构的可维护与可扩展性有很高要求。
本课题结合现代 Web 技术与 AWS Serverless 架构，设计并实现一个具备上传、转码、播放、互动、管理和统计能力的视频点播平台。既满足了基础业务，也提供了一种实践思路，即借助对象存储、函数计算、工作流编排和事件驱动机制，将Serverless技术融入视频业务。
1.1 课题背景
平台系统需要全面的前端页面展示，后端要包含视频上传、转码、封面抽取、流媒体播放、评论互动、收藏订阅以及运营统计等能力。
传统视频平台通常采用自建服务器或云主机集群，常驻式转码服务、消息中间件完成上传后的处理流程。在业务规模稳定、资源投入充足的情况下具有一定优势，但固定资源池可能出现高峰期资源不足、低峰期资源闲置的问题，且多服务多中间件会带来大量运维成本，部署和开发难度大，系统整体复杂度高，不适合快速响应新业务试错需求。
Serverless 是云计算的一种模型[1]。以平台即服务为基础，提供以对象存储、函数计算和工作流编排为代表的技术，为视频平台提供了新的架构思路。Serverless 能够按需启动计算资源，通过事件驱动方式组织媒体处理流程，将大文件上传、异步转码和状态回写等步骤解耦，降低基础设施维护成本，提高系统扩展能力[2]。本文方案可为中小规模视频点播业务提供参考。
基于上述背景，本文选择以 AWS Serverless 架构为核心，结合 Next.js 16、React 19、PostgreSQL、Prisma、FFmpeg、HLS 和 Better Auth 等技术，设计并实现一套视频点播平台。
1.2 研究的目的和意义
本课题的研究目的在于设计并实现一个基于 AWS Serverless 架构的视频点播平台，构建涵盖视频上传、媒体处理、内容发布、在线播放和数据采集的完整业务流程。系统需要支持首页浏览、搜索、频道展示、视频播放、评论互动、收藏与播放列表、内容管理以及统计分析等核心能力；此外，还需要重点验证 Serverless 技术在视频点播场景中的适用性。
结合现实业务情况，中小团队或新业务在建设视频平台时，更关注开发效率、部署成本和扩展能力。本文结合Serverless和现代Web技术，并引入 LocalStack 进行本地仿真验证，提供了一种较低成本、便于扩展的架构。
1.3 研究内容
对于平台的基础权限设计，系统按照游客、注册用户和创作者三个层次进行划分。游客可访问公开内容；注册用户在此基础上具备评论、点赞、订阅、收藏和播放列表等互动能力；创作者则进一步具备视频上传、内容管理和数据统计等能力。这样的角色划分既满足了平台基础业务需求，也避免了引入过于复杂的权限体系。
系统围绕首页浏览、视频播放、评论互动、创作者工作室和统计分析等核心模块展开，完成了前后端主要功能模块的设计与实现。
对于重点的媒体处理部分，本文设计并实现了基于 AWS Serverless 思路的视频处理流水线，利用对象存储、工作流编排与云函数，将上传后的转码、封面提取和状态回写组织为可追踪的异步流程，并借助 LocalStack 完成本地仿真验证。
 
第2章	相关技术与可行性分析
2.1 Serverless 架构概述
在 Serverless 平台上，开发人员无需直接管理底层服务器和常驻计算资源，但仍需要完成函数代码开发、权限配置、事件触发器配置和部署管理等工作。与传统服务器架构相比，Serverless 将更多基础设施运维职责交由云平台承担。通常服务以函数计算、事件驱动、对象存储为核心。能够在流量波动时动态分配资源，每个服务完成任务后云平台会自动回收资源。
对于视频点播平台，视频发布过程本身包含大量异步处理任务，其访问压力和任务持续时间也有强波动性。如果采用传统服务架构，需要维护转码服务、消息队列、任务调度器和存储服务。Serverless 架构将上传、转码、处理、状态同步等环节拆分为独立任务，非常适合这个场景[3]。
本项目采用前端应用 + 数据库 + 对象存储 + 工作流编排 + 云函数的云技术组合。Web 应用负责发起上传与播放请求，视频源文件存入对象存储，Step Functions 组织多个 Lambda 阶段任务，EventBridge 负责媒体处理链路中的事件传递，内部接口将任务状态写入数据库，前端页面再通过轮询读取处理进度。
2.2 Next.js 16 与 React 19
Next.js是一个用于构建全栈Web应用程序的React框架。使用React来构建用户界面，并提供额外的功能和优化。React基于函数式编程思想控制组件，以状态驱动的用户交互。本系统采用两者构建前端，实现了页面路由、服务端渲染与前端交互。
两者的组合很适合本系统在前端交互和工程化等方面的要求，也有较强的前端可扩展性，可以快速在此基础上二次开发。
2.3 PostgreSQL 与 Prisma
视频点播平台需要大量业务实体，数据存在较强的结构化关联关系。因此，系统需要数据库能够提供事务能力、关系建模能力以及良好的查询性能。PostgreSQL是一种特性非常齐全的关系型数据库管理系统，具备事务一致性、扩展性、数据类型丰富等优点，适合用于平台核心业务数据[4]。
Object–relational mapping（ORM）是在关系型数据库与编程语言之间转换数据的技术[5]。相当于在程序内部创建了一个虚拟的对象数据库，程序可以像操作普通对象那样对持久化数据进行管理。本系统选用Prisma 作为 ORM 工具实现数据模型定义与数据库访问[6]。Prisma 可以通过一个统一的 Schema 文件描述表、类型、约束和索引等定义，再生成TypeScript类型安全的数据访问接口，降低了开发复杂度。Prisma 在此基础上还支持基于条件的聚合搜索，以及原子性事务更新，能够较方便地实现频道统计功能。
2.4 AWS相关服务
2.4.1 S3 对象存储
Amazon S3 是 AWS 提供的高可用对象存储服务，适合存储图片、视频、日志以及其他非结构化文件。对于视频点播平台来说，原始视频文件体积较大，且转码后还会生成主清单、分片文件与封面图，如果全部存入应用服务器本地磁盘，不仅扩展困难，也不利于多实例部署与统一访问。
本系统使用对象存储管理视频源文件与处理产物，并将资源按不同用途划分到多个桶中：原始视频存放于 vod-raw，HLS 输出资源存放于 vod-hls，缩略图与封面图存放于 vod-image。用户上传视频时，系统先由服务端生成预签名上传地址，客户端再直接将 MP4 文件上传至对象存储，从而减少应用服务器带宽压力。转码完成后，HLS 主清单和切片文件继续写入对象存储，播放页面通过主清单地址完成流媒体访问[7]。
2.4.2 Lambda云函数
Lambda 是AWS提供的一种事件驱动的无服务器函数即服务，会在事件触发时执行代码并自动管理计算资源，适合完成多步骤可拆分的异步任务。
本项目将媒体处理流程拆分为多个函数阶段。每个Lambda实例运行在微虚拟机驱动的轻量环境，启动快占用低，以Lambda实现事件驱动。
2.4.3 Step Functions 工作流编排
AWS Step Functions 针对多Lambda编排提供了基于状态机的工作流编排能力，可以对多步骤任务进行顺序控制、失败中断和错误重试[8]。
本系统使用 Step Functions 对Lambda进行编排，在任意阶段异常时能通知用户并记录。还配置了失败重试策略。
2.4.4 EventBridge 事件总线
EventBridge 在本系统中主要用于媒体处理链路中的事件分发。转码 Lambda 会发布 pipeline.stage 事件，并回调内部接口将当前阶段写入数据库；前端工作室页面通过轮询读取任务状态，从而展示视频处理进度。
2.5 FFmpeg 与 HLS 流媒体技术
FFmpeg 是多媒体处理领域中使用广泛的开源工具，支持几乎所有常用功能。HLS是基于HTTP的自适应码率流媒体传输协议[9]，将完整视频切分为多个片段，通过 m3u8 清单文件控制播放行为，实现了流式传输与动态码率切换。
转码使用 FFmpeg 处理用户上传的源文件，检测媒体信息，二次编码，提取封面图，最后切片。生成的封面图以及 master.m3u8 与 seg_*.ts 切片文件会保存到对象存储。播放页与服务器对接实现在线视频播放。在实际在线视频场景中，HLS 及相关自适应流媒体方案已被广泛用于低时延视频传输与播放优化[10]。
2.6 Better Auth 认证机制
Better Auth 是一个通用 TypeScript 身份验证和授权框架。提供全面的鉴权功能。Better Auth与Next.js结合能够迅速搭建鉴权基础建设，如基本的注册登录。在项目中结合Better Auth维护一个统一的鉴权管理模块，能够同时维护密码登录，第三方OAuth绑定，以及后续可以继续扩展的企业化鉴权，多因素认证等高级需求。
本系统采用 Better Auth 认证并结合 Prisma将用户、会话、账号绑定持久化到 PostgreSQL。系统支持邮箱密码登录和 GitHub 与 Google 第三方登录。这套鉴权会配合平台其它所有模块实现权限控制与登录态管理。
2.7 可行性分析
2.7.1 技术可行性 
本系统所选技术相互之间兼容性很强。Next.js 与 React实现前端交互和API路由，PostgreSQL 与 Prisma 负责结构化业务数据，无跨编程语言障碍，全流程覆盖TypeScript类型安全。而Serverless服务则是完成了视频上传的复杂核心流程。
同时，开发阶段使用 LocalStack 对Serverless进行本地仿真，极大地方便了开发调试。这套技术栈很适合视频点播场景，可行性较高。
2.7.2 经济可行性 
Serverless按需使用资源。对于中小规模视频流量，按需付费是首要考虑的模式。 Serverless随任务触发动态运行，成本结构符合场景，同时还节省了大量开发和运维成本。
本项目采用 LocalStack 进行开发阶段的大部分本地联调，能够进一步降低试错成本。因此方案具备较好的经济可行性。
2.7.3 运行和维护可行性 
Serverless 的基础设施由云平台承担，无需长期维护独立的转码服务器池和复杂的分布式服务，维护压力较小。借助EventBridge的事件能力也便于后续业务能力继续扩展。因此系统在运行管理与后续维护方面具备较好的可行性。
 
第3章	需求分析
3.1 系统角色分析
3.1.1 游客 
游客是未登录系统的普通访问者，可浏览首页、搜索页、公开视频页和频道页。其核心需求是快速发现内容并稳定播放视频，因此系统需要提供公开内容浏览、关键词搜索、视频详情查看和频道访问等基础能力。游客不具备评论、订阅、收藏和工作室管理等写操作权限。
3.1.2 注册用户 
注册用户在游客能力基础上拥有更完整的互动权限和内容组织能力。登录后，用户可以完成点赞、点踩、评论、回复评论、订阅频道，以及加入收藏夹、稍后再看和自定义播放列表等操作。系统需要通过稳定的会话管理和权限校验保证其个性化使用体验。
3.1.3 创作者 
创作者指具备视频上传、编辑与统计查看权限的注册用户。除普通观看者能力外，创作者还需要在工作室中完成视频上传、处理状态跟踪、内容编辑、发布管理和统计分析等操作。因此，系统必须支持视频生命周期管理、任务状态反馈以及频道和视频数据查看等能力。

3.3 非功能需求分析
3.3.1 性能需求
系统需要应对大文件上传的场景，并保证在线播放的使用稳定性。首页、搜索页和统计页等查询需求要确保不陷入常规的数据库慢查询问题，Lambda转码需要FFmpeg调优减少二次编码情况，前端注意性能优化，避免常见的React卡顿问题，确保系统流畅。
3.3.2 可用性需求
系统需要为转码任务可能出现的超时、异常任务实现任务恢复机制。后台提供重试接口或是自动指数退避，支持用户在前端手动触发重试或系统自动处理，确保业务不会中断在某个环节。
3.3.3 安全需求
系统应通过认证基建完成Session管理机制，如常见的HttpOnly与Secure Cookie策略。接口安全如工作室接口要有强校验，禁止违规和越权操作，并根据视频可见性实施访问控制。 
第4章	系统设计
视频点播平台与一般信息管理系统相比，既包含账号、内容、评论、播放列表和统计分析等常见业务模块，又包含视频上传、异步转码、HLS 分发和任务状态回写等媒体处理链路。系统既要考虑页面组织、服务分层和数据库结构，也要关注媒体流水线的职责拆分、状态一致性和部署方式。
本章围绕系统总体架构、业务流程、功能模块、数据库、接口以及部署与本地仿真环境展开设计说明。相关设计均以项目当前实现为基础，强调前端页面、服务端逻辑、数据库模型与 Serverless 媒体处理流程之间的协同关系。
4.1 系统总体架构设计
系统总体架构决定功能模块之间的关系边界，也决定了后续实现是否具备清晰的扩展路径。结合本项目技术栈与业务特点，平台采用“统一 Web 应用 + 关系数据库 + 对象存储 + 工作流编排 + 云函数处理”的总体模式。该架构将页面渲染、数据存储与异步媒体处理相分离，实现了大文件直传与任务解耦。
4.1.1 系统整体架构
系统由三大服务构成：Next.js 服务、PostgreSQL 数据库以及 AWS Serverless 服务。Next.js 负责前端页面与后端逻辑，常规模块如页面访问、评论互动、视频管理和统计查询等请求由前端发起，经由 Next.js 提供的 REST API 访问 PostgreSQL 数据库并返回响应。对于复杂的视频异步处理，系统使用以 Lambda 为核心的一系列 Serverless 技术实现。媒体处理流程主要包括元数据提取、视频转码、HLS 切片上传、封面提取、结果回写以及失败标记等阶段，整体由 Step Functions 进行编排；任一阶段失败时，状态机会按预设策略进行重试、记录并回调后端。
Next.js和Serverless服务分别负责不同的任务，但两者在协同工作时联系紧密。对于即时同步任务和异步等待任务，系统分别用合适的架构实现，从而互相解耦。具体的系统架构如图4-1所示。

基础设施层即为Serverless服务，负责对象存储、云函数、流程编排和本地仿真环境的配置与运行。配置IAM权限和S3存储桶信息，维护每个Lambda执行的业务代码。转码Lambda额外使用FFmpeg，在LocalStack环境下配置dockerfile，预先拉取FFmpeg到Lambda实例。

5.1 用户认证模块
用户认证模块采用统一认证内核 + 多入口登录 + 会话化鉴权的方案。系统在登录方式上同时支持邮箱密码和第三方 OAuth，两类入口共享同一套会话机制，避免不同登录方式产生行为分叉。在数据层，认证核心实体由用户、会话、第三方账号绑定和校验记录构成，既能满足基础登录注册，也能后续账号绑定与安全扩展。用户认证时序如图5-1所示。

 
图5-1 用户认证时序图

系统在服务端完成认证内核初始化，在统一入口处理认证请求。邮箱密码登录与第三方登录（GitHub、Google）一同管理接入，共享同一会话签发机制。第三方登录后系统会请求获取用户资料授权，如果是首次登录就自动注册并使用第三方资料配置用户信息。
前端实现采用统一认证客户端，登录页与注册页只负责触发认证动作和处理交互状态。邮箱登录、社交登录、注册提交都带有回调地址，认证成功后统一跳转并结合提示信息反馈结果；失败时通过错误映射层把底层错误码转换为可读中文提示。登录态消费采用会话订阅机制，导航栏可实时切换“登录按钮”与“头像菜单”，并支持会话退出。
用户登录成功后，认证服务会生成会话令牌，一份写入 HttpOnly Cookie，另一份存到数据库，并记录用户标识与过期时间；后续请求时，服务端根据 Cookie 中的令牌检查会话是否存在且未过期即可完成验证。会话生命周期7天有效，并按默认周期刷新。在第三方登录场景下，OAuth 的 access token、refresh token 等信息会与会话令牌分层管理：前者用于账号绑定能力，后者用于站内登录态鉴权。
对于需要鉴权的请求，系统先从 Cookie 识别用户身份；随后根据接口类型执行分级校验：读取类接口使用可选身份获取逻辑，未登录时返回匿名可见数据，已登录时附加用户相关数据；写入类或隐私类接口若会话缺失、令牌失效或用户不存在，则立即中断流程并统一返回 401 未授权响应。

5.2 首页浏览与搜索模块实现
首页浏览与搜索模块是系统的内容发现入口。用户进入平台，首先快速看到可播放视频，并能够通过关键词检索内容。首页负责以流式方式展示可公开访问的视频内容，搜索页负责根据用户输入的关键词返回匹配结果。
首页通过 app/page.tsx 加载 VideoGallery 组件，并统一放置在 BrowseShell 页面框架中，从而保持导航栏和浏览区域的一致布局。视频数据由前端组件在首次渲染后调用 /api/videos 接口分批获取。后端在 lib/server/videos.ts 中通过 getVideos 和 getVideosByType 完成查询逻辑，返回 deletedAt = null、visibility = PUBLIC、processingStatus = READY 的视频记录。查询结果通过游标字段 cursor 实现分页。前端 VideoGallery 组件结合 IntersectionObserver 监听底部触发区域，在用户下滑页面时自动继续请求下一批数据，形成连续滚动的浏览体验。
搜索功能与首页浏览共用相同的内容展示风格，但数据组织方式更偏向服务端查询。导航栏组件 HomeNavbar 内置搜索框，用户输入关键词后按下回车或点击搜索按钮，页面会跳转到 /search?q=关键词。搜索页在 app/search/page.tsx 中直接读取查询参数，并调用 searchVideos 完成服务端查询。该函数同样只检索公开且处理完成的视频，并在标题、简介和频道名称三个字段上执行不区分大小写的模糊匹配。为了让更具代表性的视频优先展示，系统按播放量降序、发布时间降序返回结果。最终结果由 VideoGridSection 组件统一渲染，这样首页、搜索页和其它视频列表页在视觉结构上保持了一致性，也降低了前端重复实现的复杂度。

5.3 视频播放与互动模块实现
视频播放与互动模块是系统实现内容消费的核心部分。用户从首页或搜索页进入视频详情页后，能稳定完成播放，围绕当前视频继续执行评论、点赞点踩、订阅频道、收藏、稍后再看和加入播放列表等互动操作。本模块重点实现播放器加载媒体资源，并保证用户在观看过程中的各种互动行为可以被及时处理和上报。

5.4 视频上传与媒体处理模块实现
视频上传与媒体处理模块是AWS Serverless 架构在本课题中应用最集中的环节。视频处理不仅要保存数据，还要处理体积较大的原始视频文件，并在上传完成后自动完成转码、封面提取、切片和状态回写。本模块借助状态机编排云函数，把复杂媒体处理过程拆分为多个可观测的异步阶段。

 
图5-8 媒体处理时序图

如图5-8所示，媒体处理从工作室中的上传入口开始，系统先静默创建视频草稿，并返回原始视频上传所需的预签名地址。前端获得上传地址就能直接将视频文件上传至 vod-raw 桶，完全不经过Next.js服务端，直接和存储桶建立连接。
上传完成后前端调用创建视频接口，系统生成 UploadSession 和 TranscodeJob 作为一次转码工作记录的开始，启动 Step Functions 并编排 Lambda 先后完成元数据和封面提取、HLS 转码并调用内部API接口，前端轮询获取当前任务状态与阶段。任务成功结束，视频状态会由 PROCESSING 变为 READY，任务失败，系统将错误信息写入数据库，并支持前端请求重试或取消。
前端上传界面如图5-9和5-10所示。用户在工作室选择 MP4 视频后，客户端首先调用 /api/uploads/video-url 获取预签名上传地址。后端在 getVideoUploadUrl 中会先创建视频草稿记录，为视频生成唯一 shortCode，并同步创建一条 UploadSession 记录，用于保存本次上传对应的对象键、存储桶和过期时间。随后客户端使用 XMLHttpRequest 将视频文件直接上传到对象存储中的 vod-raw/{shortCode}/source.mp4，并通过上传进度回调实时更新前端百分比显示。文件成功写入对象存储后，前端再调用 /api/videos 通知后端“上传已完成”，由服务端正式创建 TranscodeJob，并调用 startTranscodeExecution 启动 Step Functions 状态机开始编排Lambda。

 
图5-9 视频上传框

 
图5-10 视频上传转码流程展示

转码任务启动后，系统会在 vod-hls 存储桶中为当前视频创建以 shortCode 为前缀的输出目录，并将状态切换为 PROCESSING。Step Functions 按顺序驱动各阶段 Lambda 执行处理逻辑。调用内部接口将任务置为 RUNNING，同时把视频状态更新为 PROCESSING；接口/api/internal/vod/stage 用于在提取元数据、执行转码、上传 HLS 切片、提取封面和上传封面等环节更新状态；处理成功后写入 VideoAsset 表，并将视频状态更新为 READY；任一阶段失败则通过 /api/internal/vod/mark-failed 将任务和视频统一标记为 FAILED。详细流程如图5-11所示。
系统处理完成后会把 HLS 主清单 master.m3u8、变体清单和切片文件统一保存到 vod-hls 桶中，同时将封面图存图片桶，并在数据库中为这些产物创建 VideoAsset 记录。finalize 回调会把 HLS 主清单记为主资源，并在有缩略图时同步更新 Video.thumbnail 字段。后续播放页和工作室页面都可以直接通过数据库读取资源状态，不需要再次查询对象存储。前端在转码启动后轮询获取当前任务的 jobStatus、pipelineStage、attempt和错误信息，传递给 TranscodingStep 组件进行分阶段展示。

5.6 数据统计与分析模块实现
数据统计与分析模块把前台播放行为和互动行为统一整理成可绘制成图表的统计数据。本模块在设计上先后为前台播放器和互动接口采集原始数据，再在数据库中完成日级汇总，最后由工作室页面把结果以图表和指标的形式展示出来。
数据采集层主要依赖两类来源。一是播放器行为数据。播放页中的 VideoPlayer 会在播放开始、继续播放、暂停、拖动、周期性进度上报和播放结束等操作，触发请求 /api/videos/[shortCode]/playback-events 接口写入 VideoPlaybackEvent 表。包括eventType、sessionId、播放位置、观看时长增量、播放速率、静音状态、音量以及来源信息等字段。二是互动行为数据，即点赞、点踩、评论和订阅等业务写入行为。这些数据分别记录在对应的单独表中。
系统通过 prisma/rollup.daily.sql 中定义的存储过程 sp_rollup_daily_stats，将原始播放事件和互动记录聚合成 VideoDailyStat 与 ChannelDailyStat 两张日级统计表。该存储过程会以日期范围为边界，对播放事件表中的 PLAY_START 统计观看次数，对 watchDeltaMs 汇总观看时长，并对用户标识与会话标识进行去重统计观众数。同时把视频互动表中的点赞、点踩和评论增长量按日期汇总，并进一步基于视频日统计结果和订阅数据生成频道日统计结果，统计图表如图5-15所示。
 
图5-15 数据分析页面

后端通过 lib/server/stats.ts 提供统一的数据读取逻辑。getStatPageData 用于频道级数据分析页面，会读取最近 30 天的 ChannelDailyStat 数据，并生成观看次数、观看时长、净增订阅和视频发布数等汇总指标，同时还会结合视频分组结果和视频排行榜生成内容结构图和视频表现榜单。getVideoAnalyticsPageData 则面向单视频分析页面，按最近 30 天读取 VideoDailyStat，并输出单视频的观看趋势、观看人数、观看时长、点赞增长和评论增长等细粒度指标。这样，统计分析不再直接依赖原始播放日志全表查询，而是建立在轻量级日汇总表之上，从而显著降低了图表页面的实时查询压力。
前端使用多张指标卡、折线图、订阅流动图、内容类型分布图以及视频排行榜表格，集中展示频道层面的整体运营情况；单视频分析页进一步分析单个视频的数据，展示累计观看、近 30 天观看、观看人数、观看时长、互动变化以及按日明细趋势。

结　论
本文完成了一个基于 AWS Serverless 架构的视频点播平台设计与实现。系统结合 Next.js、PostgreSQL、Prisma 以及 AWS Serverless 相关服务，完成了视频上传、媒体处理、在线播放、互动和统计分析等主要功能，并在本地仿真环境下验证了整体方案的可行性。
回顾整个实现过程，Serverless 架构在降低基础设施维护压力、提升异步任务解耦能力方面具有明显优势，但在视频转码这类资源消耗较高的场景中，也对工作流编排、异常恢复和状态一致性提出了更高要求。本文通过引入 Step Functions、事件驱动机制和任务状态回写流程，增强了媒体处理链路的可观测性与可恢复性。与此同时，LocalStack 虽然降低了开发调试成本，但与真实云环境在 IAM 权限、网络行为等方面仍存在一定差异。
本文方案验证了 AWS Serverless 架构在中小规模视频点播场景中的应用可行性。若进一步面向生产环境，还需要继续完善自适应码率策略、内容审核机制以及更接近真实云环境的部署与测试方案。
