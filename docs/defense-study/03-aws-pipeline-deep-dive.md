# AWS 媒体处理链路专项（补 Step Functions 与 EventBridge）

## 一句话全链路

前端拿预签名地址直传原视频到 `vod-raw`，后端创建任务并启动状态机，状态机编排多个 Lambda 完成转码与切片，结果写入 `vod-hls`/`vod-image`，最后回写数据库并由前端轮询展示。

## 服务职责对照

- S3：存文件，不管业务状态。
- Lambda：做具体计算任务（提取元数据、转码、封面、回调）。
- Step Functions：管流程顺序、重试、失败分支。
- EventBridge：发处理阶段事件，便于扩展订阅方。
- Next.js 内部接口：把任务状态与产物落库。

## 为什么必须引入状态机

- 处理链路是多步骤异步任务，不适合塞进一个函数。
- 失败控制要统一，否则容易出现“半成功”。
- 状态机可视化有助于定位卡点。

## 你要背下来的状态变化

1. UPLOADING：文件上传中。
2. PROCESSING：状态机已启动。
3. READY：转码和资源写入完成。
4. FAILED：任一关键阶段失败并统一标记。

## 高频追问标准答法

### 问：为什么不直接一个 Lambda 跑完整流程？

答：单函数会把流程控制、重试策略、错误处理耦合在一起，定位问题困难；状态机可以分阶段治理，失败可控且可观测。

### 问：EventBridge 的实际价值是什么？

答：当前它承载阶段事件分发，让链路具备“发布-订阅”扩展能力。后续接告警、审计、运营分析时，不用改核心转码逻辑。

### 问：LocalStack 和真实 AWS 有什么差异？

答：LocalStack 适合开发联调与流程验证，但在 IAM、网络行为和云上托管细节上与真实 AWS 仍有差异，生产前必须做真实云环境验证。
