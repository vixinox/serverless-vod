# 核心知识讲解（通俗版 + 技术版 + 追问点）

## 1) 什么是 Serverless

通俗版（20秒）：

以前要自己买机器、配服务、守着运维。Serverless 是把这些基础设施交给云平台，你只管写业务逻辑，系统按请求自动扩缩，按使用量计费。

技术版（60-90秒）：

本项目把视频业务拆成同步与异步两类：同步请求由 Next.js API 处理；异步媒体处理由 Step Functions 编排 Lambda 执行。视频文件进入对象存储后触发状态机，阶段状态通过内部接口回写数据库，前端轮询展示进度，实现计算与业务解耦。

追问点：

- 为什么不是传统常驻转码集群。
- Serverless 在成本与运维上的收益。
- 冷启动和可观测性如何处理。

## 2) 为什么视频上传要用预签名 URL

通俗版（20秒）：

用户把大文件直接传到对象存储，不经过业务服务器，速度更稳，也不容易把后端带宽打爆。

技术版（60-90秒）：

后端先创建视频草稿和 UploadSession，返回预签名 URL。前端用 PUT 直传 `vod-raw/{shortCode}/source.mp4`。上传完成后再调用创建转码任务接口，启动状态机。这样后端只负责授权与状态管理，不承担大流量文件中转。

追问点：

- 安全边界在哪里。
- Content-Type 和过期时间如何控制。

## 3) 为什么选 HLS

通俗版（20秒）：

HLS 会把长视频切成很多小片段，播放器按网络情况连续拉取，不卡顿时体验更稳。

技术版（60-90秒）：

FFmpeg 对源视频转码并切片，输出 `master.m3u8` 与 `seg_*.ts`。播放端读取主清单后按分片拉流。HLS 能兼容主流浏览器和设备，适合点播场景，也方便后续多码率扩展。

追问点：

- HLS 与 MP4 直链相比优势。
- 与 DASH 方案如何取舍。

## 4) 为什么要用 Step Functions

通俗版（20秒）：

把“提取信息-转码-切片-封面-回写”这串步骤交给状态机统一调度，失败就重试或走失败分支，不会乱。

技术版（60-90秒）：

状态机负责阶段顺序、错误捕获和重试策略。任一步失败进入 `MarkFailed` 路线，回调内部接口统一标记任务与视频状态，保证数据库状态一致，避免出现“文件处理失败但页面显示处理中”的脏状态。

追问点：

- 重试策略怎么定。
- 为什么不写在单个 Lambda 里。
- 为什么不做消息队列。

**为什么不用消息队列（SQS/Kafka）替代 Step Functions：**

消息队列擅长解耦并发消费，适合"大量同质任务、消费者无状态"的场景；视频处理管道的特点恰好相反：阶段之间有严格顺序依赖（必须先提取元信息才能转码，转码完成才能切片），每个任务是有状态的长流程，而不是一批可乱序处理的消息。

用消息队列实现相同效果，需要自行维护"阶段编排逻辑"——为每个阶段单独建队列，Lambda 消费完一个阶段后手动投递到下一个队列，失败时自己写重试和死信逻辑，任务整体状态靠外部数据库手动跟踪。Step Functions 把这些内置了：状态转移、条件分支、错误捕获、重试策略全部声明在状态机定义里，可视化调试，出错时精确定位在哪一步。

一句话总结：**消息队列管"谁来干"，Step Functions 管"按什么顺序干、出错怎么办"**，对有序多阶段管道，后者更合适。

## 5) EventBridge 在项目中的作用

通俗版（20秒）：

它像事件总线，负责把“当前处理到哪一步了”广播出来，系统更容易扩展。

技术版（60-90秒）：

转码阶段会发布 `pipeline.stage` 事件，并调用内部接口把阶段状态落库。现在前端用轮询读取数据库，后续可增加告警、审计、统计等订阅方，不用改核心处理链路。

追问点：

- 既然前端轮询，为何还需要事件总线。
- 未来扩展价值是什么。

## 6) 为什么要做数据库触发器维护计数

通俗版（20秒）：

点赞、评论、订阅变化很多，靠应用层手动加减容易漏。触发器在数据库层自动维护更稳。

技术版（60-90秒）：

在 `triggers.core.sql` 中维护点赞数、评论数、回复数、订阅数等聚合计数，避免并发写入下计数偏差，降低应用层重复逻辑。

追问点：

- 触发器性能影响。
- 与异步汇总任务如何配合。
