# 5 系统实现

在前文完成需求分析与系统设计之后，本章结合项目当前代码实现，对视频点播平台各功能模块的落地情况进行说明。与第四章偏重结构划分和设计方案不同，本章重点回答“系统具体是如何实现的”。因此，本章将从页面组织、接口处理、服务层封装、数据库状态维护以及 Serverless 媒体处理链路五个角度，对用户认证、内容浏览、视频在线播放、评论互动、播放列表、视频上传、创作者工作室和统计分析等功能进行展开说明。

本系统基于 Next.js 16 的 App Router 组织页面与接口，前端页面主要位于 app/ 目录下，接口通过 app/api/ 下的 Route Handler 提供，核心业务逻辑集中在 lib/server/ 中封装，数据存取通过 Prisma 访问 PostgreSQL，媒体处理链路则由 lib/localstack.ts、内部回调接口以及本地仿真的 Step Functions、Lambda 和 S3 共同完成。通过这种实现方式，系统形成了“统一 Web 应用承载交互，数据库承载业务状态，对象存储承载媒体文件，状态机驱动异步处理”的完整工程闭环。

按照指导意见，本章以“文字说明 + 关键流程图 + 页面截图”的方式组织内容。其中，流程较简单、界面展示特征更明显的模块以截图说明为主；认证控制、评论交互、播放链路、上传转码流水线和统计汇总等业务关系较复杂的模块，则保留必要的时序图或流程图，以增强实现过程的说明性。

## 5.1 用户认证与权限控制实现

用户认证模块采用 Better Auth 与 Prisma 适配器实现。系统在 lib/auth.ts 中完成认证实例配置，将 user、session、account 和 verification 等认证相关表与 PostgreSQL 关联，并开启邮箱密码登录方式，同时预留 GitHub 与 Google 第三方登录能力。app/api/auth/[...all]/route.ts 将 Better Auth 封装为统一认证入口，从而承担注册、登录、获取会话和退出登录等请求。登录页与注册页分别通过 app/login/page.tsx 和 app/signup/page.tsx 提供，客户端表单组件 components/login-form.tsx 与 components/signup-form.tsx 则负责收集用户输入并调用认证接口。

在权限控制方面，系统并未将会话判断分散在各个页面或接口中，而是通过 lib/server/auth-session.ts 提供 getOptionalUserId() 和 requireUserId() 两个统一入口。对于首页、搜索页和公开播放页等匿名可访问场景，服务层调用 getOptionalUserId() 读取可选会话，以决定是否返回用户个性化状态；对于评论发布、频道订阅、播放列表管理、视频上传、工作室访问和统计分析等必须登录的场景，则通过 requireUserId() 强制校验身份，未登录时直接拦截请求。这种实现方式使页面权限、接口权限与服务层权限保持一致，避免了逻辑分散带来的遗漏问题。

除基础登录态之外，系统还实现了用户偏好设置持久化。app/api/settings/route.ts 提供主题偏好读取和更新接口，lib/server/settings.ts 将数据写入 user_settings 表，hooks/use-settings.ts 则在客户端通过 SWR 与本地缓存同步主题配置，保证登录用户在不同页面中能够保持统一的界面偏好。

## 5.2 首页浏览与搜索功能实现

首页浏览与搜索功能主要围绕公开视频列表查询展开。首页入口为 app/page.tsx，页面通过 VideoGallery 组件组织视频卡片流，并使用 BrowseShell 统一页面布局。视频列表数据由 app/api/videos/route.ts 提供，服务层调用 lib/server/videos.ts 中的 getVideos() 方法完成分页查询。该方法在数据库层限定 deletedAt 为空、visibility 为 PUBLIC、processingStatus 为 READY 的视频才能进入公开列表，同时根据 LONG 与 SHORT 两类内容分别返回游标分页结果。这一实现保证了首页不会提前暴露草稿、私有视频或尚未转码完成的视频。

搜索页入口为 app/search/page.tsx。页面从查询参数中读取关键词后，调用 searchVideos() 按视频标题、简介和频道名称进行模糊匹配，并按照观看量和发布时间排序结果。由于搜索逻辑与首页共享相同的公开视频过滤条件，因此系统能够在“首页推荐”和“关键词检索”之间保持一致的内容访问边界。对于用户而言，首页负责内容发现，搜索页负责目标定位，两者最终都归结为对公开视频资源的安全读取。

在页面表现上，首页和搜索页共用视频网格组件，视频卡片统一展示缩略图、标题、频道作者、播放量和发布时间等信息；在数据获取上，则通过接口层和服务层分离的方式提升可维护性。后续若需要增加分区推荐、排序切换或瀑布流加载，也可以在现有实现上继续扩展。

## 5.3 视频播放与推荐功能实现

视频播放页位于 app/watch/[shortCode]/page.tsx，是系统前台消费链路的核心页面。页面首次加载时会并发调用 getVideoInfo() 与 getWatchSidebarData() 两个服务函数，分别获取视频基础信息、频道信息、当前用户互动状态以及右侧播放列表上下文。getVideoInfo() 中实现了较完整的访问控制逻辑：对于公开和不公开视频，非作者只有在视频转码完成后才能访问；对于私有和草稿视频，则只有作者本人能够查看，其他用户会被重定向到登录页或直接拒绝访问。通过这种方式，系统在播放页层面实现了内容可见性和处理状态的双重控制。

视频资源地址优先使用已配置的 CDN 域名；若开发环境未配置 CDN，则退回到 /api/hls/[...objectKey] 代理接口读取 HLS 清单和分片。播放器组件 VideoPlayer 基于 HLS 主清单地址进行播放，视频详情区 VideoInfo 展示标题、频道信息、点赞、收藏和订阅等操作入口，评论区 CommentArea 用于展示和提交评论，侧边栏 RecommendationList 负责推荐其他公开视频。推荐数据由 getRecommendation() 生成，其内部通过随机查询从公开视频集合中选取候选内容，保证当前页面可以形成连续观看体验。

为了支撑后续统计分析，系统在播放过程中还通过 /api/videos/[shortCode]/playback-events 接口上报播放行为事件。recordPlaybackEvent() 会将播放开始、播放进度、暂停、恢复、拖动和结束等行为写入 VideoPlaybackEvent 表，并保存会话标识、播放位置、观看时长增量和浏览器环境信息，为后续的日级统计汇总提供原始数据来源。

## 5.4 评论互动功能实现

评论互动模块以播放页为主要入口，其后端实现集中在 lib/server/comments.ts 中。系统通过 app/api/videos/[shortCode]/comments/route.ts 提供评论列表查询与评论发布接口，通过 app/api/comments/[commentId]/replies/route.ts 提供回复分页与回复新增接口，通过 app/api/comments/[commentId]/reaction/route.ts 提供评论点赞和点踩接口。主评论查询支持“按热度排序”和“按时间排序”两种模式，其中热门排序以 likesCount 和创建时间作为联合游标条件，最新排序则以时间和主键构造分页游标。这种实现方式保证了评论区在数据规模增长后仍然具备可扩展的分页能力。

在前端交互方面，hooks/use-comments.ts 与 hooks/use-replies.ts 基于 SWR 实现评论和回复的增量加载，并在新增评论、删除评论、更新评论和切换点赞状态时执行乐观更新，从而减少用户等待感。评论内容提交前会进行非空校验，服务端还会校验视频或父评论是否存在。对于未登录用户，服务层在进入写操作前会直接触发身份校验，确保评论区写入能力只对登录用户开放。

评论模块中的计数字段维护并不是在应用层手工累加，而是交由数据库触发器完成。prisma/triggers.core.sql 中定义了评论计数、评论回复数以及评论点赞数维护逻辑：当评论新增或删除时，自动更新 Video.commentsCount 与父评论的 repliesCount；当评论互动表发生变化时，自动更新 Comment.likesCount 与 Comment.dislikesCount。这种实现降低了应用层并发写入下出现计数不一致的风险。

## 5.5 频道展示、订阅与用户内容页实现

频道页位于 app/channel/[name]/page.tsx，其数据由 getChannelPageData() 统一装配。该函数首先按频道名称读取频道基础信息和创作者资料，再查询频道下所有公开且已处理完成的视频，同时统计公开视频数量和累计观看量。页面在视觉上将频道横幅、创作者头像、订阅人数、加入时间和最新视频列表整合在一起，使频道既承担内容聚合入口，也承担创作者展示页的作用。

订阅功能通过 app/api/channels/[channelId]/subscription/route.ts 暴露，底层调用 toggleSubscribe() 对 Subscription 表进行新增或删除操作。系统在实现中显式禁止用户订阅自己的频道，并在数据库层通过触发器自动维护 Channel.subscribersCount。这样一来，频道页、播放页中的订阅按钮，以及统计页中的订阅增长分析，都可以共享同一组订阅关系数据。

除频道页之外，系统还提供了围绕当前用户的内容页。app/history/page.tsx 通过 getHistoryVideos() 展示观看历史，读取 VideoPlaybackEvent 中最近一次观看记录；app/saved/page.tsx 则基于收藏夹和稍后再看两类系统播放列表，展示用户已保存的视频集合。相比单纯的频道展示，这两类页面体现了系统已经从“内容发布”扩展到“内容留存与回访”的用户内容组织能力。

## 5.6 收藏夹与播放列表功能实现

播放列表模块由系统播放列表和自定义播放列表两部分组成。系统播放列表包括“稍后再看”和“收藏夹”，其核心逻辑由 toggleSystemPlaylistVideo() 实现。当用户在播放页点击保存按钮时，系统首先检查目标视频是否具备可保存条件：若视频属于当前用户，则允许直接保存；若视频属于他人，则必须满足公开视频或不公开视频且转码完成的条件。之后系统在事务中自动创建或复用对应的系统播放列表，并向 PlaylistItem 表中添加或移除记录，同时维护 position 字段和列表更新时间。

自定义播放列表相关功能位于工作室接口中，由 listUserPlaylists()、createPlaylist()、updatePlaylist()、deletePlaylist() 与 listPlaylistItems() 等服务函数提供支撑。播放列表默认只允许所有者维护，且通过 systemKey 区分系统列表与自定义列表，防止用户误修改系统默认结构。列表项通过 playlistId + position 的唯一约束保持顺序稳定，当视频被加入或移出列表时，系统会自动调整后续项的位置编号，从而保证连续播放和顺序浏览的正确性。

在前台页面上，播放页右侧可以读取当前视频所属的播放列表并展示 PlaylistPanel，用户也可以通过收藏页和稍后再看页回看已保存内容；在后台页面上，创作者可在工作室中创建和管理自定义播放列表。至此，系统不仅支持“看视频”，也支持“组织视频”和“按主题继续看”。

## 5.7 视频上传与媒体处理流水线实现

视频上传与媒体处理流水线是本系统最具工程特点的部分。与普通内容管理系统只处理表单文本不同，本系统需要完成视频草稿创建、对象存储直传、转码任务入队、状态机调度、HLS 切片、封面抽取、任务状态回写以及失败恢复等多个步骤。整个流程由上传接口、数据库模型、LocalStack 仿真的 S3/Step Functions/Lambda 以及内部回调接口共同组成。

### 5.7.1 上传会话与对象存储实现

上传入口由 app/api/uploads/video-url/route.ts 提供，底层调用 getVideoUploadUrl()。当创作者选择视频文件后，系统首先调用 createUploadVideoDraft() 创建视频草稿，并为其生成唯一短码；若当前用户尚未拥有频道，ensureChannelForUser() 会自动创建频道记录，将视频与创作者频道关联起来。随后，系统依据视频短码生成对象存储键 {shortCode}/source.mp4，调用 createUploadPresignedUrl() 生成预签名上传地址，并写入 UploadSession 记录。

前端上传逻辑由 hooks/use-video-upload.ts 管理。该 Hook 使用 XMLHttpRequest 直接向对象存储执行 PUT 请求，并通过上传进度事件实时更新状态，从而避免应用服务器承担大文件中转压力。上传完成后，前端再调用 /api/videos 通知服务端启动后续媒体处理流程。通过“先申请上传地址，再直传对象存储，最后创建任务”的设计，系统将大文件传输与业务状态创建解耦，显著降低了 Web 应用在上传场景下的带宽压力。

### 5.7.2 元数据提取实现

在上传完成后，createVideo() 会根据已完成的 UploadSession 创建 TranscodeJob 记录，并调用 startTranscodeExecution() 启动状态机。状态机启动后首先进入元数据提取阶段，该阶段对应内部回调接口 /api/internal/vod/update-metadata。该接口在收到 jobId 和 videoId 后，通过事务将转码任务状态更新为 RUNNING，将视频状态更新为 PROCESSING，同时记录任务启动时间与尝试次数。

虽然元数据的具体探测工作由 Lambda 侧结合 FFprobe 和 FFmpeg 完成，但在应用侧，这一阶段最核心的职责是建立“任务已开始执行”的一致性状态，并为后续时长、分辨率和封面等元信息回写预留字段。工作室页面中的处理中提示，正是依赖这一阶段写入的 processingStatus 与 TranscodeJob.status 字段才能及时更新。

### 5.7.3 转码与 HLS 切片实现

转码与 HLS 切片阶段是整个流水线的核心执行环节。系统通过 FFmpeg 将原始 MP4 视频转换为 master.m3u8 及分片文件，并将产物上传至 vod-hls 桶。为了增强处理过程的可观测性，Lambda 在关键阶段会回调 /api/internal/vod/stage，将 job_started、downloading、probing、transcoding、uploading_segments、thumbnail_extracting 和 thumbnail_uploading 等阶段标识写入 TranscodeJob.pipelineStage 字段。

这一设计使前端不必依赖难以稳定表达的百分比进度，而是可以展示更贴近实际处理链路的阶段提示，例如“正在探测视频信息”“正在转码切片”“正在上传媒体分片”等。对于视频在线播放而言，当 master.m3u8 上传完成并在最终阶段回写后，播放页即可通过对象存储代理接口或 CDN 域名读取 HLS 资源。

### 5.7.4 封面抽取与状态回写实现

在转码阶段完成后，状态机进入收尾阶段，对应内部接口 /api/internal/vod/finalize。该接口会根据 Lambda 回传的信息统一完成三类数据写入。第一，更新 TranscodeJob 状态为 SUCCEEDED，清空阶段标识并记录结束时间；第二，更新 Video 状态为 READY，写入 readyAt、视频时长以及缩略图访问地址；第三，向 VideoAsset 表写入 HLS_MASTER 资产记录，并在存在封面图时写入 THUMBNAIL 资产记录。

在封面图地址构建方面，系统支持两种访问方式：若配置了图片 CDN 域名，则使用 https://域名/对象键 的形式返回；若处于本地开发环境，则退回到 LocalStack 的对象访问地址。为了保证重试场景下的数据幂等性，finalize 在写入新的 HLS_MASTER 和 THUMBNAIL 资产前，会先删除旧记录，避免同一视频在重复执行成功后出现资产重复的问题。

### 5.7.5 异常处理与任务纠偏实现

媒体处理链路天然存在转码失败、执行超时、用户主动取消和状态机异常中断等风险。为此，系统提供了多层次的异常处理机制。首先，状态机异常会统一回调 /api/internal/vod/mark-failed，由该接口将 TranscodeJob 和 Video 一并收敛为 FAILED 状态，并记录错误信息；其次，创作者可以通过 /api/studio/videos/[shortCode]/retry 和 /api/studio/videos/[shortCode]/cancel 发起重试和取消操作，其中 retryVideoJob() 会复用历史任务输入重新创建任务，cancelVideoJob() 则会停止状态机执行并将本地任务收敛到终态。

此外，系统还实现了僵尸任务纠偏机制。/api/internal/vod/reconcile-stale 会扫描长时间停留在 QUEUED 或 RUNNING 状态的任务，在确认不存在其他活跃任务后，将这些异常记录统一修正为 FAILED，并同步修正视频的处理状态。这样可以防止工作室页面长期显示“处理中”而实际任务早已失效，从而提升系统整体的一致性和可维护性。

## 5.8 创作者工作室与内容管理实现

创作者工作室承担系统后台管理入口的职责，其页面主要位于 app/studio/ 目录下。app/studio/contents/page.tsx 通过 ContentsPanel 展示当前用户的视频内容列表，app/studio/contents/video/[id]/page.tsx 则基于 getVideoDetails() 提供单视频编辑页，用于维护标题、简介、封面、可见性和质量信息。服务层中的 listUserVideos()、editVideo()、deleteVideo()、getProcessingStatuses() 和 getPipelineStatus() 等方法，分别支撑工作室列表查询、视频编辑、软删除以及任务状态轮询。

工作室实现的关键点在于它并不是简单的静态后台，而是一个持续感知媒体任务状态的动态控制台。上传文件后，useVideoUpload() 会进入轮询状态，周期性读取 /api/videos/[shortCode]/pipeline-status 返回的处理结果，并将上传、提交任务、转码中、完成或失败等状态同步到界面中。当任务失败时，工作室允许用户直接发起重试或取消；当任务成功后，编辑表单能够继续维护视频基础信息并进入发布阶段。

除了视频内容管理外，工作室还集成了自定义播放列表管理能力和统计分析入口。系统将创作者在内容生产、列表组织和数据查看中的高频操作集中到统一工作区内，从而形成从“上传视频”到“管理视频”再到“分析视频”的闭环体验。

## 5.9 统计分析模块实现

统计分析模块面向创作者提供频道级和单视频级两类分析能力。频道统计页位于 app/studio/stat/page.tsx，其数据由 getStatPageData() 提供；单视频分析页位于 app/studio/stat/[shortCode]/page.tsx，其数据由 getVideoAnalyticsPageData() 提供。页面通过多个统计卡片、趋势图、订阅流图、内容类型环形图、榜单表格和明细探索组件，将聚合后的数据进行可视化展示。

在数据来源上，统计模块并不直接对原始事件表进行大范围实时聚合，而是采用“原始行为记录 + 日级汇总结果”的双层实现。播放页上报的行为事件被写入 VideoPlaybackEvent 表，评论、点赞和订阅等业务数据则通过业务表和触发器持续维护累计状态；随后，prisma/rollup.daily.sql 中定义的 sp_rollup_daily_stats 存储过程会按照日期范围，将播放行为、互动行为和发布行为汇总到 VideoDailyStat 与 ChannelDailyStat 两张表中。这样一来，统计页只需读取相对稳定的日级汇总数据，即可快速生成近 7 天、近 14 天或近 30 天的趋势结果。

从实现效果看，频道统计页主要展示 30 天观看次数、观看时长、净增订阅和发布视频数，并给出频道整体趋势与视频榜单；单视频分析页则进一步展示某条视频的累计观看、独立观众、观看时长和互动增量。这一模块标志着系统不再停留在基础点播和上传管理层面，而是已经具备面向创作者运营分析的数据支撑能力。
