# 2 相关技术与可行性分析

本章结合本系统“基于 AWS Serverless 架构的视频点播平台设计与实现”的建设目标，对项目所依赖的核心技术进行说明，并从技术、经济以及运行维护三个方面分析系统的可行性。通过对前端框架、数据持久化方案、云服务组件、流媒体处理技术和认证机制的梳理，可以为后续的系统设计与实现提供理论基础和技术支撑。

## 2.1 Serverless 架构概述

Serverless 并不意味着系统中不存在服务器，而是指开发者无需直接管理底层服务器资源，应用的计算、扩缩容、运行调度和部分运维能力由云平台负责。该模式通常以函数计算、事件驱动、托管存储和托管工作流为核心，能够在业务请求到来时动态分配资源，在空闲阶段自动回收资源，从而提升资源利用率并降低系统运维复杂度。

对于视频点播平台而言，视频上传、转码、切片、封面抽取和状态回写等任务具有明显的异步处理特征，其访问压力和任务持续时间也呈现出较强的波动性。如果采用传统常驻式服务架构，需要持续维护转码服务、消息队列、任务调度器和存储服务，整体部署复杂，扩展成本较高。相比之下，Serverless 架构更适合将上传完成、转码开始、处理失败、状态同步等环节拆分为独立事件，在对象存储、函数计算和工作流编排的协同下形成完整的媒体处理链路。

本项目采用“前端应用 + 数据库 + 对象存储 + 工作流编排 + 云函数”的组合模式构建视频点播平台。其中，用户侧通过 Web 应用发起上传与播放请求；视频源文件存入对象存储；Step Functions 负责组织多个 Lambda 阶段任务；EventBridge 负责发布流水线阶段事件；处理结果最终回写数据库并反馈到前端页面。该方案体现了 Serverless 架构模块解耦、弹性伸缩、按需执行和事件驱动的典型特点，能够较好适配视频点播业务中“高峰上传、异步处理、结果回显”的场景需求。

## 2.2 Next.js 16 与 React 19

Next.js 是面向 React 生态的全栈 Web 开发框架，具备路由组织、服务端渲染、接口处理、静态资源管理以及前后端协同开发等能力。React 则通过组件化思想组织界面，实现状态驱动的用户交互。二者结合后，能够兼顾首屏渲染效率、界面复用能力和工程组织规范，适合构建功能较完整的视频平台前端。

本系统前端采用 Next.js 16 与 React 19 实现。项目基于 `app` 目录组织页面，涵盖首页浏览、搜索、登录注册、频道页、视频播放页、创作者工作室、统计分析页等功能模块。系统同时结合 Route Handler 提供接口访问能力，并通过 Server Action 承担部分服务端调用逻辑，使页面渲染、数据获取与业务操作能够在统一工程内协同完成。相比传统前后端完全分离模式，该方案减少了接口重复封装和上下文切换成本，有助于提升开发效率。

在具体实现中，首页视频流采用客户端增量加载方式提升浏览体验；播放页结合视频详情、推荐内容、评论互动和权限提示展示完整内容消费场景；工作室页面则面向创作者提供视频管理、转码任务控制和统计分析能力。React 19 的组件化和状态管理方式能够支持上传进度展示、转码轮询、播放器交互和评论回复等动态场景，而 Next.js 提供的服务端能力则便于完成登录态校验、页面级数据预取和受保护资源访问控制。

因此，Next.js 16 与 React 19 的组合不仅满足系统在交互性、工程化和页面组织方面的要求，也为后续扩展搜索、推荐、统计面板等复杂模块提供了良好的前端基础。

## 2.3 PostgreSQL 与 Prisma

视频点播平台涉及用户、频道、视频、评论、订阅、收藏、播放列表、上传任务、转码任务以及统计数据等多类业务实体，这些数据之间存在较强的结构化关联关系。因此，系统需要具备稳定事务能力、关系建模能力以及良好的查询性能。PostgreSQL 作为成熟的开源关系型数据库，具备事务一致性好、扩展性强、数据类型丰富、查询能力完善等优点，适合承载平台核心业务数据。

本系统选用 PostgreSQL 作为主数据库，并使用 Prisma 作为 ORM 工具实现数据模型定义与数据库访问。Prisma 可以通过统一的 Schema 文件描述实体、枚举、索引和关系约束，再由客户端生成类型安全的数据访问接口，从而降低 SQL 拼写错误和类型不一致问题。在本项目中，数据库层定义了 `User`、`Channel`、`Video`、`Comment`、`Subscription`、`Playlist`、`UploadSession`、`TranscodeJob`、`VideoAsset`、`VideoPlaybackEvent`、`VideoDailyStat`、`ChannelDailyStat` 等核心模型，能够较完整地覆盖点播平台从内容生产到内容消费的业务闭环。

其中，`Video` 模型用于记录视频标题、可见性、处理状态、发布时间、观看次数等核心属性；`VideoAsset` 用于描述源文件、HLS 主清单、分片资源和缩略图等媒体资产；`TranscodeJob` 用于追踪队列状态、执行阶段、失败原因和任务完成时间；`VideoPlaybackEvent` 与日统计表则用于支撑播放行为采集和可视化分析。Prisma 在此基础上还支持基于条件的聚合、分组统计和事务更新，使系统能够较方便地实现频道统计、排行榜、观看时长汇总等功能。

因此，PostgreSQL 提供了可靠的数据持久化基础，Prisma 提供了高效且类型安全的数据访问方式，二者结合能够满足本系统在数据一致性、可维护性和开发效率方面的要求。

## 2.4 AWS 相关服务

本系统围绕 AWS Serverless 技术栈设计媒体处理流程，核心使用对象存储、函数计算、工作流编排和事件总线四类云服务。在开发阶段，项目引入 LocalStack 对相关云服务进行本地仿真，以降低调试成本并提升开发效率；在部署层面，则能够平滑迁移到真实 AWS 环境。

### 2.4.1 Amazon S3 对象存储

Amazon S3 是 AWS 提供的高可用对象存储服务，适合存储图片、视频、日志以及其他非结构化文件。对于视频点播平台来说，原始视频文件体积较大，且转码后还会生成主清单、分片文件与封面图，如果全部存入应用服务器本地磁盘，不仅扩展困难，也不利于多实例部署与统一访问。

本系统使用对象存储承载视频上传和媒体产物管理，并将资源按不同用途划分到多个桶中：原始视频存放于 `vod-raw`，HLS 输出资源存放于 `vod-hls`，缩略图与封面图存放于 `vod-image`。用户上传视频时，系统先由服务端生成预签名上传地址，客户端再直接将 MP4 文件上传至对象存储，从而减少应用服务器带宽压力。转码完成后，HLS 主清单和切片文件继续写入对象存储，播放页面通过主清单地址完成流媒体访问。

这种设计将大文件传输从 Web 业务服务中解耦出来，有助于降低上传链路中的服务器压力，并提高文件管理的一致性和可扩展性。

### 2.4.2 AWS Lambda 云函数

AWS Lambda 是一种事件驱动的无服务器计算服务，能够在指定事件触发后执行函数逻辑，并按调用量和执行时长进行计费。相较于常驻式转码服务，Lambda 更适合承载步骤清晰、触发明确、可拆分执行的异步处理任务。

本项目将媒体处理流程拆分为多个函数阶段，包括元数据提取、视频转码、封面抽取、结果回写和失败标记等步骤。上传完成后，系统根据视频信息创建转码任务，再通过工作流触发各阶段 Lambda 执行。元数据提取阶段负责将任务状态置为运行中并更新视频处理状态；转码阶段调用 FFmpeg 完成编码、切片和封面截图；收尾阶段负责写入 `VideoAsset`、更新 `Video.thumbnail` 并将视频状态改为 `READY`；失败阶段则在异常发生时将任务收敛到 `FAILED` 状态。

Lambda 的引入使每一阶段的职责边界更加清晰，也便于后续根据业务需要单独增强某个处理环节，例如增加多码率转码、字幕处理或 AI 内容审核等能力。

### 2.4.3 AWS Step Functions 工作流编排

视频处理并非单一函数即可完成，而是由多个顺序相关、可能失败且需要重试的步骤组成。若仅依靠应用代码手工串联这些步骤，会导致流程控制复杂、异常恢复困难，并增加状态不一致风险。AWS Step Functions 提供了状态机式的工作流编排能力，能够对多步骤任务进行顺序控制、失败捕获、条件分支和重试管理。

本系统使用 Step Functions 对媒体处理流水线进行编排。上传完成后，平台以视频编号、任务编号、输入桶、输出桶、对象键和视频类型等信息作为执行输入启动状态机。状态机依次驱动“提取元数据”“执行转码”“完成回写”等步骤，并在任意阶段异常时统一流转到失败处理逻辑。系统还针对失败收敛链路配置重试策略，以提升任务最终状态的一致性，避免前端长期停留在处理中状态。

通过 Step Functions 进行工作流编排后，媒体处理链路的执行顺序更加明确，任务状态也更易于观察和维护，这对于视频平台中大量异步任务的治理具有重要意义。

### 2.4.4 Amazon EventBridge 事件总线

在媒体流水线运行过程中，仅依靠最终成功或失败结果并不足以支撑前端状态展示和任务监控。平台还需要感知“开始下载源文件”“探测元数据”“执行转码”“上传切片”“上传缩略图”等关键阶段，以向用户提供更细粒度的进度反馈。Amazon EventBridge 提供了事件分发能力，适合在服务之间解耦传递状态变化信息。

本系统在转码 Lambda 的关键节点发布 `pipeline.stage` 事件，并同步回调内部接口，将当前阶段写入数据库中的 `TranscodeJob.pipelineStage` 字段。前端工作室页面通过轮询方式获取视频处理状态和当前阶段，从而展示更具可解释性的任务进度。例如，系统可区分任务当前处于“下载源文件”“探测视频信息”还是“上传分片”阶段，而不是简单地显示“处理中”。

因此，EventBridge 在本系统中承担了阶段事件广播与状态同步的作用，提高了处理链路的可观测性，也为后续接入告警、通知、审计等能力预留了扩展空间。

## 2.5 FFmpeg 与 HLS 流媒体技术

FFmpeg 是广泛应用于多媒体处理领域的开源工具集，支持音视频转码、格式转换、封面截取、分片封装和元数据探测等功能。HLS 是一种基于 HTTP 的流媒体传输协议，其核心思想是将完整视频切分为多个较短片段，并通过 `m3u8` 清单文件组织播放顺序，使客户端能够以分段方式加载媒体内容。

在视频点播业务中，直接播放用户上传的原始 MP4 文件往往存在兼容性差、首帧时间长、断点恢复能力弱等问题。相比之下，HLS 方案能够更好地适配浏览器与移动端播放器，同时便于与 CDN、对象存储和权限控制机制配合。播放器只需先请求主清单，再按需拉取后续分片，即可实现更平滑的在线播放。

本系统在转码环节使用 FFmpeg 对用户上传的 MP4 文件进行处理，完成视频探测、HLS 切片、主清单生成和缩略图抽取等工作。处理完成后，系统将 `master.m3u8` 与 `seg_*.ts` 切片文件写入对象存储，并将封面图保存到独立的图片桶中。播放页面则通过 HLS 地址向播放器提供媒体源，实现在线视频播放。对于长视频场景，该方案能够在保证播放兼容性的同时，将媒体处理流程与页面播放流程有效分离。

因此，FFmpeg 与 HLS 技术共同构成了本系统视频处理与在线播放的核心基础，是实现“上传后自动转码、转码后立即播放”业务闭环的重要技术支撑。

## 2.6 Better Auth 认证机制

视频点播平台不仅包含公开浏览能力，还涉及用户注册登录、创作者工作室、评论互动、收藏夹、播放列表和频道管理等功能，因此必须建立稳定的身份认证与权限控制机制。认证方案既要支持基础的账号登录，也要兼顾第三方登录扩展能力，并能够方便地与前端页面和数据库模型整合。

本系统采用 Better Auth 实现认证机制，并结合 Prisma 适配器将用户、会话、账号绑定和校验信息持久化到 PostgreSQL 中。系统已支持邮箱密码登录，同时预留 GitHub 与 Google 第三方登录方式。认证完成后，平台基于会话信息识别当前用户身份，并在视频编辑、播放列表管理、评论操作、订阅、工作室访问以及上传转码任务控制等场景中进行权限校验。

从工程实现上看，Better Auth 与 Next.js 的结合较为自然，既便于服务端读取登录态，也便于客户端发起登录与登出操作。对于本项目而言，该方案能够在较低开发成本下实现较完善的认证闭环，并为后续扩展多因素认证、账号绑定或更精细化的角色控制提供良好基础。

## 2.7 可行性分析

在完成技术选型说明之后，还需要从实际落地角度评估该视频点播平台的可行性。结合项目当前实现情况，可以从技术、经济以及运行维护三个方面进行分析。

### 2.7.1 技术可行性

从技术实现角度看，本系统所选用的技术组件之间具有较好的兼容性与协同性。前端层使用 Next.js 16 与 React 19，能够同时满足页面渲染、组件交互和服务端业务处理需求；数据层使用 PostgreSQL 与 Prisma，可以较稳定地承载平台的结构化业务数据；媒体处理层使用 S3、Lambda、Step Functions、EventBridge 和 FFmpeg，能够覆盖视频上传、异步转码、状态同步和结果回写等核心流程。

从项目当前实现情况看，系统已经完成视频上传、转码、HLS 播放、评论互动、频道展示、收藏与播放列表、创作者管理和统计分析等功能，说明技术链路已经能够支撑完整业务闭环。此外，项目在开发阶段通过 LocalStack 对对象存储、函数计算、工作流和事件总线进行本地仿真，既降低了调试门槛，也验证了整体方案具备较强的工程可实施性。因此，该系统在技术层面具备明确的实现路径和较高的可行性。

### 2.7.2 经济可行性

从经济角度分析，Serverless 架构的一个重要优势在于按需使用资源。对于中小规模视频平台而言，早期业务量通常有限，如果直接采购和长期维护固定规模的转码服务器、对象存储网关和任务调度服务，容易造成资源闲置和前期投入过高。而基于 Serverless 的视频处理链路可以在有上传任务时再触发函数执行，在无任务时几乎不占用计算资源，整体成本结构更符合渐进式建设需求。

本项目采用对象存储保存视频源文件和转码结果，避免将大量媒体文件保存在应用服务器本地磁盘，降低了扩容和备份压力；开发阶段又通过 LocalStack 完成大部分本地联调，减少了真实云资源的试错成本。对于毕业设计或中小型原型系统而言，该方案能够在较低基础投入下完成完整功能验证，具备较好的经济可行性。

### 2.7.3 运行与维护可行性

从运行维护角度看，Serverless 架构将大量基础设施职责交由云平台承担，系统维护重点更多转向业务逻辑、任务监控和异常恢复。相较于传统转码集群方案，本系统无需长期维护独立的转码服务器池和复杂的分布式调度组件，维护压力相对较小。

与此同时，本项目已在实现中引入状态阶段回写、失败收敛、任务重试、僵尸任务纠偏和统计分析等机制，能够提升系统运行过程中的可观测性与可恢复性。前端工作室可轮询获取任务状态，服务端可对长时间停滞的任务进行对账与修正，数据库中也保留了转码任务、播放事件和日统计数据，便于问题追踪与性能分析。由于系统模块划分较清晰，后续若需要扩展推荐算法、CDN 分发、多清晰度转码或审核机制，也可以在现有结构上逐步演进。因此，该平台在运行管理与后续维护方面具备较好的可行性。

综上所述，本系统所采用的技术路线能够有效匹配视频点播平台的业务特点，且在技术实现、成本投入和运行维护三个方面均具有较强的可行性，为后续的系统设计与实现奠定了扎实基础。
