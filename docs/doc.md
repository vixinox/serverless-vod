第1章	绪论
随着移动互联网、宽带网络和智能终端的普及，在线视频已成为互联网内容消费的重要形态。无论是长视频平台、短视频平台，还是在线教育、企业培训和活动回看系统，视频点播都已经成为数字内容传播的基础能力。与图文类业务相比，视频业务在数据规模、处理链路和分发方式上更为复杂，尤其是在上传、转码、存储、分发和播放等环节，对系统架构的弹性、稳定性和可维护性提出了更高要求。因此，围绕视频点播平台的设计与实现展开研究，具有较强的现实意义和工程价值。
本课题面向中小规模视频业务场景，结合现代 Web 技术与 AWS Serverless 架构，设计并实现一个具备上传、转码、播放、互动、管理和统计能力的视频点播平台。论文在关注系统功能实现的同时，也讨论如何借助对象存储、函数计算、工作流编排和事件驱动机制提升开发效率与资源利用率，从而为同类业务提供一种可复用的实践思路。
1.1	课题背景
  近年来，在线视频业务持续增长，用户对视频内容的访问场景也日益多样化，视频平台从单纯的内容展示逐渐转向“内容生产、处理、分发、互动、分析”一体化发展。与此相对应，平台系统不再只需要支持前端页面展示，还必须具备视频上传、异步转码、封面抽取、流媒体播放、评论互动、收藏订阅以及运营统计等完整能力。尤其是在用户自主上传视频的业务场景中，视频源文件大小不一、清晰度和编码格式各异，给平台在媒体处理和资源调度方面带来了显著挑战。
传统视频平台通常采用自建服务器或云主机集群来承载媒体处理任务，通过常驻式转码服务、消息中间件和分发组件完成上传后的处理流程。这类方案在业务规模稳定、资源投入充足的情况下具有一定优势，但其短板也较为明显：一方面，视频处理任务具有波峰波谷明显、资源占用高的特点，资源池容易出现高峰期不足、低峰期闲置的问题；另一方面，转码服务、文件存储、任务调度和状态管理等模块往往需要分别部署和维护，系统整体复杂度较高，难以快速响应新业务试错需求。
在云计算快速发展的背景下，以对象存储、函数计算和工作流编排为代表的 Serverless 技术逐渐成熟，为视频平台提供了新的架构思路。相较于传统架构，Serverless 架构能够按需启动计算资源，通过事件驱动方式组织媒体处理流程，将大文件上传、异步转码和状态回写等步骤解耦，降低基础设施维护成本，并提高系统的扩展能力。对于中小型视频平台、教学实验项目或新业务验证场景而言，这种方式具有较高的适用性。
基于上述背景，本文选择以 AWS Serverless 架构为核心，结合 Next.js 16、React 19、PostgreSQL、Prisma、FFmpeg、HLS 和 Better Auth 等技术，设计并实现一套视频点播平台，并围绕其架构合理性与工程可行性展开研究。
1.2	研究目的与意义
本课题的研究目的在于设计并实现一个基于 AWS Serverless 架构的视频点播平台，构建从视频上传、媒体处理、内容发布到在线播放和行为采集的业务闭环。在功能层面，系统需要支持首页浏览、搜索、频道展示、视频播放、评论互动、收藏与播放列表、内容管理以及统计分析等核心能力；在架构层面，则重点验证 Serverless 技术在视频点播场景中的适用性。
从理论意义看，视频点播平台兼具 Web 应用与媒体处理系统的双重特征，既涉及前端交互、数据建模和权限控制，也涉及大文件上传、异步转码和流媒体封装等问题。将现代 Web 开发技术与 Serverless 媒体处理流程结合起来，有助于为相关课题研究和工程实践提供参考。
从实践意义看，中小团队或新业务在建设视频平台时，更关注开发效率、部署成本和后续扩展能力。本文通过对象存储、工作流编排、云函数和关系型数据库构建整体方案，并引入 LocalStack 进行本地仿真验证，为类似业务提供了一种较低门槛、便于扩展的视频平台建设思路。
1.3	研究内容
围绕“基于 AWS Serverless 架构的视频点播平台设计与实现”这一主题，本文的主要研究内容包括三个方面。
首先，完成系统需求分析与总体架构设计。结合视频平台的典型业务场景，对游客、注册用户和创作者等角色进行划分，分析平台在浏览、播放、互动、上传、管理和统计等方面的核心需求，并据此设计系统整体结构和数据流转关系。
其次，完成视频点播平台的主要功能实现。系统围绕内容浏览、视频在线播放、评论互动、频道展示、播放列表、工作室管理和统计分析等模块展开，形成前台消费与后台管理相结合的业务框架。
再次，完成基于 AWS Serverless 思路的媒体处理流水线设计与实现。系统利用对象存储、工作流编排和云函数组织视频上传后的异步处理流程，并结合状态反馈机制实现任务跟踪。在此基础上，对系统的可行性和应用价值进行总结分析。
 
第2章	技术与可行性分析
本章结合本系统“基于 AWS Serverless 架构的视频点播平台设计与实现”的建设目标，对项目所依赖的核心技术进行说明，并从技术、经济以及运行维护三个方面分析系统的可行性。通过对前端框架、数据持久化方案、云服务组件、流媒体处理技术和认证机制的梳理，可以为后续的系统设计与实现提供理论基础和技术支撑。
2.1	Serverless 架构概述
Serverless 并不意味着系统中不存在服务器，而是指开发者无需直接管理底层服务器资源，应用的计算、扩缩容、运行调度和部分运维能力由云平台负责。该模式通常以函数计算、事件驱动、托管存储和托管工作流为核心，能够在业务请求到来时动态分配资源，在空闲阶段自动回收资源，从而提升资源利用率并降低系统运维的复杂度。
对于视频点播平台而言，视频上传、转码、切片、封面抽取和状态回写等任务具有明显的异步处理特征，其访问压力和任务持续时间也呈现出较强的波动性。如果采用传统常驻式服务架构，需要持续维护转码服务、消息队列、任务调度和存储服务，整体部署复杂，扩展成本较高。相比之下，Serverless 架构更适合将上传完成、转码开始、处理失败、状态同步等环节拆分为独立事件，在对象存储、函数计算和工作流编排的协同下形成完整的媒体处理链路。
本项目采用“前端应用 + 数据库 + 对象存储 + 工作流编排 + 云函数”的组合模式构建视频点播平台。其中，用户侧通过 Web 应用发起上传与播放请求；视频源文件存入对象存储；Step Functions 负责组织多个 Lambda 阶段任务；EventBridge 负责发布流水线阶段事件；处理结果最终回写数据库并反馈到前端页面。该方案体现了 Serverless 架构模块解耦、弹性伸缩、按需执行和事件驱动的典型特点，能够较好适配视频点播业务中“高峰上传、异步处理、结果回显”的场景需求。
2.2	Next.js 16 与 React 19
Next.js 是面向 React 生态的 Web 开发框架，具备路由组织、服务端渲染、接口处理、静态资源管理以及前后端协同开发等能力。React 则通过组件化思想组织界面，实现状态驱动的用户交互。二者结合后，能够兼顾首屏渲染效率、界面复用能力和工程组织规范，适合构建功能较完整的视频平台前端。
本系统前端采用 Next.js 16 与 React 19 实现，项目基于 app 目录组织首页、搜索、播放页、频道页、登录注册页和创作者工作室等页面，并结合 Route Handler 与 Server Action 完成数据获取和业务操作。相比传统前后端完全分离模式，该方案减少了接口重复封装和上下文切换成本，有助于提升开发效率。
因此，Next.js 16 与 React 19 的组合能够较好满足本系统在交互性、工程化和页面组织方面的要求，也为后续功能扩展提供了良好的前端基础。
2.3	PostgreSQL 与 Prisma
视频点播平台涉及用户、频道、视频、评论、订阅、收藏、播放列表、上传任务、转码任务以及统计数据等多类业务实体，这些数据之间存在较强的结构化关联关系。因此，系统需要具备稳定事务能力、关系建模能力以及良好的查询性能。PostgreSQL 作为成熟的开源关系型数据库，具备事务一致性好、扩展性强、数据类型丰富、查询能力完善等优点，适合承载平台核心业务数据。
本系统选用 PostgreSQL 作为主数据库，并使用 Prisma 作为 ORM 工具实现数据模型定义与数据库访问。Prisma 可以通过统一的 Schema 文件描述实体、枚举、索引和关系约束，再由客户端生成类型安全的数据访问接口，从而降低 SQL 拼写错误和类型不一致问题。在本项目中，数据库层定义了 User、Channel、Video、Comment、Subscription、Playlist、UploadSession、TranscodeJob、VideoAsset、VideoPlaybackEvent、VideoDailyStat、ChannelDailyStat 等核心模型，能够较完整地覆盖点播平台从内容生产到内容消费的业务闭环。
其中，Video 模型用于记录视频标题、可见性、处理状态、发布时间、观看次数等核心属性；VideoAsset 用于描述源文件、HLS 主清单、分片资源和缩略图等媒体资产；TranscodeJob 用于追踪队列状态、执行阶段、失败原因和任务完成时间；VideoPlaybackEvent 与日统计表则用于支撑播放行为采集和可视化分析。Prisma 在此基础上还支持基于条件的聚合、分组统计和事务更新，使系统能够较方便地实现频道统计、排行榜、观看时长汇总等功能。
因此，PostgreSQL 提供了可靠的数据持久化基础，Prisma 提供了高效且类型安全的数据访问方式，二者结合能够满足本系统在数据一致性、可维护性和开发效率方面的要求。
2.4	AWS 相关服务
本章结合本系统的建设目标，对项目所依赖的核心技术进行说明，并从技术、经济以及运行维护三个方面分析系统的可行性。通过对前端框架、数据持久化方案、云服务组件、流媒体处理技术和认证机制的梳理，可以为后续的系统设计与实现提供理论基础和技术支撑。
2.4.1 S3 对象存储
Amazon S3 是 AWS 提供的高可用对象存储服务，适合存储图片、视频、日志以及其他非结构化文件。对于视频点播平台来说，原始视频文件体积较大，且转码后还会生成主清单、分片文件与封面图，如果全部存入应用服务器本地磁盘，不仅扩展困难，也不利于多实例部署与统一访问。
本系统使用对象存储承载视频上传和媒体产物管理，并将资源按不同用途划分到多个桶中：原始视频存放于 vod-raw，HLS 输出资源存放于 vod-hls，缩略图与封面图存放于 vod-image。用户上传视频时，系统先由服务端生成预签名上传地址，客户端再直接将 MP4 文件上传至对象存储，从而减少应用服务器带宽压力。转码完成后，HLS 主清单和切片文件继续写入对象存储，播放页面通过主清单地址完成流媒体访问。
2.4.2 Lambda 云函数
AWS Lambda 是一种事件驱动的无服务器计算服务，能够在指定事件触发后执行函数逻辑，并按调用量和执行时长进行计费。相较于常驻式转码服务，Lambda 更适合承载步骤清晰、触发明确、可拆分执行的异步处理任务。
本项目将媒体处理流程拆分为多个函数阶段，包括元数据提取、视频转码、封面抽取、结果回写和失败标记等步骤。上传完成后，系统根据视频信息创建转码任务，再通过工作流触发各阶段 Lambda 执行。元数据提取阶段负责将任务状态置为运行中并更新视频处理状态；转码阶段调用 FFmpeg 完成编码、切片和封面截图；收尾阶段负责写入 VideoAsset、更新 Video.thumbnail 并将视频状态改为 READY；失败阶段则在异常发生时将任务收敛到 FAILED 状态。
2.4.3 Step Functions 工作流编排
视频处理并非单一函数即可完成，而是由多个顺序相关、可能失败且需要重试的步骤组成。若仅依靠应用代码手工串联这些步骤，会导致流程控制复杂、异常恢复困难，并增加状态不一致风险。AWS Step Functions 提供了状态机式的工作流编排能力，能够对多步骤任务进行顺序控制、失败捕获、条件分支和重试管理。
本系统使用 Step Functions 对媒体处理流水线进行编排。上传完成后，平台以视频编号、任务编号、输入桶、输出桶、对象键和视频类型等信息作为执行输入启动状态机。状态机依次驱动“提取元数据”“执行转码”“完成回写”等步骤，并在任意阶段异常时统一流转到失败处理逻辑。系统还针对失败收敛链路配置重试策略，以提升任务最终状态的一致性，避免前端长期停留在处理中状态。
2.5	FFmpeg 与 HLS 流媒体技术
FFmpeg 是广泛应用于多媒体处理领域的开源工具集，支持音视频转码、格式转换、封面截取、分片封装和元数据探测等功能。HLS 是一种基于 HTTP 的流媒体传输协议，其核心思想是将完整视频切分为多个较短片段，并通过 m3u8 清单文件组织播放顺序，使客户端能够以分段方式加载媒体内容。
在视频点播业务中，直接播放用户上传的原始 MP4 文件往往存在兼容性差、首帧时间长、断点恢复能力弱等问题。相比之下，HLS 方案能够更好地适配浏览器与移动端播放器，同时便于与 CDN、对象存储和权限控制机制配合。播放器只需先请求主清单，再按需拉取后续分片，即可实现更平滑的在线播放。
本系统在转码环节使用 FFmpeg 对用户上传的 MP4 文件进行处理，完成视频探测、HLS 切片、主清单生成和缩略图抽取等工作。处理完成后，系统将 master.m3u8 与 seg_*.ts 切片文件写入对象存储，并将封面图保存到独立的图片桶中。播放页面则通过 HLS 地址向播放器提供媒体源，实现在线视频播放。对于长视频场景，该方案能够在保证播放兼容性的同时，将媒体处理流程与页面播放流程有效分离。
2.6	认证机制
视频点播平台不仅包含公开浏览能力，还涉及用户注册登录、创作者工作室、评论互动、收藏夹、播放列表和频道管理等功能，因此必须建立稳定的身份认证与权限控制机制。认证方案既要支持基础的账号登录，也要兼顾第三方登录扩展能力，并能够方便地与前端页面和数据库模型整合。
本系统采用 Better Auth 实现认证机制，并结合 Prisma 适配器将用户、会话、账号绑定和校验信息持久化到 PostgreSQL 中。系统支持邮箱密码登录，同时预留 GitHub 与 Google 第三方登录方式。认证完成后，平台基于会话信息识别当前用户身份，并在视频编辑、播放列表管理、评论操作、订阅、工作室访问以及上传转码任务控制等场景中进行权限校验。
从工程实现上看，Better Auth 与 Next.js 的结合较为自然，既便于服务端读取登录态，也便于客户端发起登录与登出操作。对于本项目而言，该方案能够在较低开发成本下实现较完善的认证闭环，并为后续扩展多因素认证、账号绑定或更精细化的角色控制提供良好基础。
2.7	可行性分析
2.7.1 技术可行性
从技术实现角度看，本系统所选用的技术组件较为成熟，且相互之间具有较好的兼容性。Next.js 与 React 可支撑页面渲染和交互实现，PostgreSQL 与 Prisma 可承载结构化业务数据，S3、Lambda、Step Functions、EventBridge 和 FFmpeg 则能够覆盖视频上传、异步转码、状态同步和结果回写等核心流程。
同时，项目在开发阶段可借助 LocalStack 对对象存储、函数计算、工作流和事件总线进行本地仿真，能够降低联调难度并验证关键链路。因此，该系统在技术层面具有明确的实现基础和较高的可行性。
2.7.2 经济可行性
从经济角度分析，Serverless 架构的优势在于按需使用资源。对于中小规模视频平台而言，若直接长期维护固定规模的转码服务器和调度服务，容易造成前期投入偏高和资源闲置；而基于 Serverless 的处理链路可以随任务触发动态运行，成本结构更符合渐进式建设需求。
同时，本项目采用对象存储保存媒体文件，并通过 LocalStack 完成开发阶段的大部分本地联调，能够进一步降低试错成本。因此，该方案具备较好的经济可行性。
2.7.3 运行与维护可行性
从运行维护角度看，Serverless 架构将大量基础设施职责交由云平台承担，系统维护重点更多转向业务逻辑、任务监控和异常恢复。相较于传统转码集群方案，该方案无需长期维护独立的转码服务器池和复杂的分布式调度组件，维护压力相对较小。
此外，平台通过状态回写、失败收敛和任务重试等机制增强链路的可观测性与可恢复性，也便于后续围绕推荐、审核或多清晰度转码等能力继续扩展。因此，该系统在运行管理与后续维护方面具备较好的可行性。
因此，本系统所采用的技术路线能够较好匹配视频点播平台的业务特点，并在技术实现、成本投入和运行维护三个方面具有较强的可行性。
 
第3章	需求分析
对于视频点播平台而言，需求不仅体现在页面展示和基础数据增删改查上，还体现在上传、转码、播放、互动和统计等多个业务链路的协同配合。结合本课题“基于 AWS Serverless 架构的视频点播平台设计与实现”的目标，以及系统当前已经形成的页面结构、接口能力与数据库模型，可以将需求概括为角色需求、功能需求和非功能需求三个方面。
3.1	系统角色分析
3.1.1 游客
游客是未登录系统的普通访问者，可浏览首页、搜索页、公开视频页和频道页。其核心需求是快速发现内容并稳定播放视频，因此系统需要提供公开内容浏览、关键词搜索、视频详情查看和频道访问等基础能力。游客不具备评论、订阅、收藏和工作室管理等写操作权限。
3.1.2 注册用户
注册用户在游客能力基础上拥有更完整的互动权限和内容组织能力。登录后，用户可以完成点赞、点踩、评论、回复评论、订阅频道，以及加入收藏夹、稍后再看和自定义播放列表等操作。系统需要通过稳定的会话管理和权限校验保证其个性化使用体验。
3.1.3 创作者
创作者本质上是进入内容生产场景的注册用户。除普通观看者能力外，创作者还需要在工作室中完成视频上传、处理状态跟踪、内容编辑、发布管理和统计分析等操作。因此，系统必须支持视频生命周期管理、任务状态反馈以及频道和视频数据查看等能力。
3.2	功能分析与用例
结合系统角色划分与项目现有模块，平台功能可归纳为用户认证、内容浏览与播放、互动与内容组织、视频上传处理以及工作室管理五个模块。各模块共同构成“内容发现、内容消费、内容生产、内容运营”的完整业务闭环。
3.2.1 用户认证模块
用户认证模块负责注册、登录、退出登录和会话保持，并为评论、收藏、订阅及工作室访问等后续操作提供身份基础。系统应支持邮箱密码登录，并预留第三方登录扩展能力。

| 用例名称 | 参与者 | 前置条件 | 结果 |
| --- | --- | --- | --- |
| 用户注册 | 游客 | 无 | 系统创建用户账号 |
| 用户登录 | 游客 | 已存在账号 | 系统建立会话并进入登录态 |
| 访问受限功能 | 游客 | 未登录 | 系统拦截并引导登录 |
| 退出登录 | 注册用户 | 已登录 | 系统清除会话 |

3.2.2 内容浏览与播放模块
该模块承担平台前台消费场景。系统需要支持首页浏览、搜索、视频播放、频道访问和推荐展示，并根据视频可见性和用户身份控制访问范围。对于创作者本人访问处理中视频时，页面还应给出明确状态提示。

互动与内容组织模块主要面向已登录用户，负责评论、点赞点踩、订阅频道以及收藏夹、稍后再看和播放列表等功能。该模块的目标是增强用户参与度和内容留存能力。

3.2.4 视频上传与媒体处理模块
视频上传与媒体处理模块是本系统的核心生产链路。系统需要支持创作者创建视频草稿、获取上传凭证、直传对象存储，并在上传完成后自动触发转码、切片、封面抽取和状态回写等异步处理流程。

工作室模块面向创作者提供内容管理和数据分析能力。系统需要支持视频信息编辑、可见性维护、任务状态查看、失败任务重试，以及频道和单视频统计结果展示。

3.3	非功能需求分析
3.3.1 性能需求
系统应通过预签名上传减轻应用服务器的大文件传输压力，并依靠 HLS 分片提升在线播放稳定性。首页、搜索页、频道页和统计页等查询场景也应保持合理响应时间，以保证整体使用流畅度。
3.3.2 可用性需求
系统需要为公开视频提供稳定播放入口，并对上传中、处理中和失败中的视频给出明确状态说明。对于转码失败或状态卡住的任务，平台应支持重试、取消和纠偏等恢复操作，以保证使用连续性。
3.3.3 安全性需求
系统应通过统一认证机制管理账号与会话信息，并对私有视频、草稿视频和工作室写操作进行严格权限控制。上传凭证和内部处理接口也应具备时效性和访问限制，避免未授权调用。
3.4	领域模型分析
从业务角度看，本系统由账号域、内容域、互动域、媒体处理域和统计域共同构成。User、Channel 和 Subscription 描述账号与频道关系；Video、UploadSession、TranscodeJob 和 VideoAsset 描述视频从上传到可播放的生命周期；Comment、VideoReaction、Playlist、PlaylistItem 和 VideoPlaybackEvent 描述内容消费与互动行为；VideoDailyStat 和 ChannelDailyStat 用于承接统计分析结果。该领域模型能够支撑平台从内容生产到内容消费再到运营分析的完整链路。
